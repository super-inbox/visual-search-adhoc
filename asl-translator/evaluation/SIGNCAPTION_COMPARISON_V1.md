# SignCaption (Sign-Speak) vs. Curify `predictions_baseline0` — comparison v1

**Status of this document:** debugging / triage comparison only. It does **not**
establish ground truth, does **not** score against `evaluation_set.json`, and
does **not** change what counts as `verified_gold` anywhere in the repo.

## Provenance

Both reference texts compared here were generated by an external commercial
tool, not by a human ASL-fluent annotator watching the signing:

```
source: Sign-Speak / SignCaption
status: external-tool candidate reference
verified: false
usable_for_official_metrics: false
```

This mirrors the existing `candidate_reference` / `usable_for_official_metrics:
false` convention used for `1320_1000022357_137.2s` (see
`asl-translator/asl-eval/README.md`), with one further caveat: 1320's candidate
was built by direct human visual inspection of burned-in captions (no OCR, no
external service). The SignCaption files here are the *opposite* case — a
third-party ASL-recognition tool's own output, with unknown internal
methodology, accuracy, and failure modes. They are evidence, not ground truth,
and if anything deserve **more** skepticism than 1320's candidate, not less.

Files compared:

| Video ID | SignCaption SRT | Curify `predictions_baseline0` JSON |
|---|---|---|
| `1477_recording_6.7s` | `ground_truth_candidates/signcaption/1477_recording_6.7s.srt` | `predictions_baseline0/1477_recording_6.7s.json` |
| `1474_1000004432_11.5s` | `ground_truth_candidates/signcaption/1474_1000004432_11.5s.srt` | `predictions_baseline0/1474_1000004432_11.5s.json` |

No `evaluation_set.json` entry exists for either video — neither is in the
official evaluation set today, and this comparison does not add one. Metrics
below were produced with the existing, unmodified
`asl-translator/asl-eval/evaluate.py` (SignCaption SRT passed as `--reference`,
Curify JSON as `--prediction`), run locally, no network calls:

```
python3 asl-translator/asl-eval/evaluate.py \
    --reference asl-translator/data/asl_corpus/ground_truth_candidates/signcaption/<video_id>.srt \
    --prediction asl-translator/data/asl_corpus/predictions_baseline0/<video_id>.json
```

Caveat this framing implies: calling SignCaption the "reference" for the
purpose of running the existing WER/CER tool is a mechanical necessity (the
tool needs one input to play that role), **not** an endorsement of SignCaption
as truth. Read every WER/CER number below as "distance between two unverified
machine outputs," not "Curify's error rate."

Timing is the one place the two systems agree: both place their (single vs.

### Word-level disagreement

- **Missing (in SignCaption, absent from Curify)**: "is", "this", "on", "d" —

  unmatched into the aligned prediction.
- **Extra (in Curify, not in SignCaption)**: 10 of Curify's 14 words are pure

- No words match verbatim between the two transcripts.

### Qualitative notes

SignCaption reads this clip as a single short yes/no question ("Is this on,
D?" — plausibly the signer checking whether a device/camera is recording,
addressed to someone named/labeled "D"). Curify's baseline0 instead produces
four short, generic, first-person statements ("I have three of them", "I know
popular English", "I don't know", and a bare "X" — likely a fingerspelled
letter or an low-confidence/garbage token). There is no shared proposition
between the two outputs. Either SignCaption mis-recognized the signing as a
question it isn't, or Curify hallucinated four unrelated statements — this
sample alone cannot distinguish the two failure modes, and quite possibly both
are wrong. The bare "X" segment in Curify is itself a known low-confidence
signal worth flagging independent of this comparison.

## Cross-case analysis: non-determinism vs. systematic disagreement

This is the question task 8 in the prior turn set up and this turn asks to
resolve. All three numbers needed are now available:

| Pair | WER | CER | Temporal IoU |
|---|---|---|---|
| SignCaption vs. 1466 | 0.9505 | 0.7119 | 0.3654 |
| SignCaption vs. 1467 | 0.9505 | 0.7016 | 0.3344 |
| **1466 vs. 1467 (self)** | **0.9706** | **0.7088** | **0.4631** |

### Observed fact

- 1466 and 1467's own mutual WER (0.9706) is **higher** (more disagreement)
  than either one's WER against SignCaption (0.9505, both). CER is in the
  same range across all three pairs (0.70–0.71).
- Temporal IoU is **higher** between 1466 and 1467 (0.4631) than between
  either one and SignCaption (0.3654 / 0.3344).
- Both baseline0 predictions were produced from the same
  `producer` string: *"Baseline 0 — gemini-2.5-flash over motion-adaptive
  sampled stills... temperature unset (default 1.0)"* (per each prediction
  JSON's own metadata) — i.e., the two runs used no fixed seed and an
  unset/default temperature by the runner's own documentation.

### Inference (directly supported by the numbers above, low speculation)

- Text-content disagreement between baseline0's own two independent runs is
  **at least as large as** its disagreement with an unrelated external tool
  (SignCaption). If baseline0 were instead systematically mistranslating
  this signer's content in one *consistent* direction, its two runs on
  identical input should resemble each other much more closely than they
  resemble a different tool's output. They don't — self-disagreement is
  numerically the largest gap of the three. This is evidence **for**
  output non-determinism as a major driver of the observed
  baseline0-vs-SignCaption gap, and evidence **against** "baseline0 has one
  stable, wrong reading of this content that differs systematically from
  SignCaption's reading."
- Timing/segmentation is comparatively more stable within baseline0 (IoU
  0.4631 self vs. 0.33–0.37 vs. SignCaption) than word-level content is.
  This is consistent with the two systems' segmentation being driven by
  different mechanisms (motion-adaptive frame sampling for baseline0 vs.
  whatever SignCaption uses internally) while baseline0's own sampler is at
  least somewhat repeatable run-to-run, even though the generated *text* for
  each sampled window is not.

### Hypothesis (plausible, not established by this data alone)

- The dominant source of baseline0's disagreement with SignCaption on this
  clip is more likely sampling noise (temperature unset/default 1.0, no
  seed) than a systematic content-understanding gap specific to this video
  — but this data cannot rule out *both* being true simultaneously (i.e.,
  baseline0 could be both noisy **and** biased away from correct content;
  noise alone doesn't require the bias to be zero).
  - Weak supporting evidence from elsewhere in this repo: comparing the
    existing `predictions_eval/*_baseline0.json` vs.
    `predictions_eval/*_temperature0.json` pairs (built for `155` and
    `1252` in earlier work, unrelated to this task) gives WER 0.09 for 155
    but WER 0.82 for 1252 — i.e., pinning `temperature=0` reduced
    baseline0-vs-temperature0 disagreement a lot on one sample and barely
    at all on the other. `asl-eval/README.md` already documents that
    "Gemini decoding is non-deterministic even at `temperature=0` in
    practice," so temperature is *a* lever, not a fix guaranteed to work.
  - **Because SignCaption itself is an unverified external tool, it is
    equally possible that SignCaption's transcript is the less accurate of
    the three** (1466, 1467, SignCaption) rather than the anchor the other
    two are failing to match. Nothing in this comparison distinguishes
    "baseline0 is noisy and wrong" from "baseline0 is noisy and SignCaption
    is wrong" from "all three are wrong in different ways." Resolving that
    requires a human-verified reference for this video, which does not
    exist today.

## Answers

### How strongly do the two systems disagree?

Very strongly, on text content, in both cases. Neither sample has more than
one word surviving a strict WER alignment, and the underlying propositions
(what the signer is asserting or asking) are unrelated between SignCaption
and Curify baseline0 in both clips — this isn't a paraphrase-vs-literal
difference the WER metric is failing to credit, the two outputs describe
different content. Timing agreement is inconsistent (strong on 1477, weak on
1474), so there's no evidence yet that one tool is a more reliable timing
anchor than the other. With only two very short clips (6.7s, 11.5s) and no
independent human-verified reference for either, it is not possible to say
*which* system (if either) is closer to what was actually signed — this
comparison only establishes that they disagree with each other, not that one
is right.

### Are these two cases useful enough to keep spending SignCaption credits on longer samples?

Marginally, but the current evidence is thin enough that it argues for one
more *targeted* run before scaling up, not for stopping or for committing to
a long batch. Two 4–11 word clips can't distinguish "SignCaption and Curify
are both unreliable on short/ambiguous clips" from "SignCaption is a useful
independent check and Curify baseline0 has real accuracy problems" — both
are consistent with what's here. What would move this forward fastest is a
sample where a *third* signal already exists to break the tie, rather than
a third pairwise unverified-vs-unverified comparison.

### Which longer sample should be run next, and why? *(resolved — see update below)*

**Update:** this recommendation was acted on. A SignCaption reference for the
`1466`/`1467` content-identical pair now exists (see Sample 3 above, and the
file-naming discrepancy flagged there), and both comparisons ran. The
original reasoning is kept below for context.

**`1466_nohead-half1_189.5s`** (rather than jumping straight to the 300s
`1442_clip01_300.0s`).

- It already has a Curify `predictions_baseline0` prediction on disk
  (`predictions_baseline0/1466_nohead-half1_189.5s.json`), so a SignCaption
  run on it is immediately scoreable with no other prep.
- Per `asl-translator/data/asl_corpus/README.md`, `1466_nohead-half1` and
  `1467_nohead-half1` are **the same underlying video content**, submitted as
  two independent production jobs 11 seconds apart (independently re-encoded,
  frame-identical). Both already have `predictions_baseline0` predictions.
  A single SignCaption run against 1466's video buys **two** comparisons for
  one credit spend: SignCaption vs. 1466's prediction *and* SignCaption vs.
  1467's prediction (the existing `run_ready.py` /
  `EXTRA_PREDICTION_PAIRINGS` mechanism already knows how to pair 1467
  against a 1466 reference once one exists).
- That pairing directly answers a sharper question than "does SignCaption
  agree with Curify": *is Curify's baseline0 closer to SignCaption on one run
  than the other, or does it disagree with SignCaption by roughly the same
  amount both times?* If baseline0's two independent runs on identical input
  disagree with each other about as much as they each disagree with
  SignCaption, that's strong evidence the problem is baseline0's own
  run-to-run non-determinism rather than anything specific to this
  comparison. If instead both runs land close to each other but both far
  from SignCaption, that points more toward a systematic gap between the
  two systems (or toward SignCaption being the less reliable side).
- It's also a meaningful step up in length (189.5s vs. the 6.7s/11.5s tested
  so far) without jumping straight to the longest available clip (1442,
  300s), so it's a reasonable next rung rather than a large, expensive leap.

Avoid `1442_clip01_300.0s` as the *next* step — it's the longest and most
expensive clip to run, and spending credits there before the 1466/1467
determinism question is answered risks re-learning the same "these two tools
disagree a lot" lesson at higher cost without adding a second reference point
per run.

### Recommended next optimization experiment (based on all three SignCaption cases: 1477, 1474, 1466/1467)

**Do not spend the next round of credits on another SignCaption comparison.
Spend it on isolating baseline0's own non-determinism first**, because the
1466/1467 result (self-disagreement WER 0.9706 ≥ SignCaption-disagreement WER
0.9505) means a fourth SignCaption clip would very likely reproduce the same
"near-total disagreement" finding without answering *why* — and right now
that "why" is the actual open question, not the disagreement's existence.

Concretely, using tooling that already exists in this repo
(`asl-eval/run_current_model.py`, documented in `asl-eval/README.md` —
requires the explicit `--run --acknowledge-private-data-upload` gate and a
real `GEMINI_API_KEY`, not executed by this task):

1. Run `--config temperature0` **twice** on the same 1466 (or 1467) video —
   i.e., produce two temperature0 predictions for one video, the same way
   1466/1467 already gives two temperature-unset (≈1.0) predictions for one
   video. This directly tests whether pinning `temperature=0` reduces
   self-disagreement versus the 0.9706 WER measured here at the default
   temperature, on the *same* content already characterized in this
   document — rather than introducing a new, uncharacterized video as an
   extra variable.
2. If temperature0-vs-temperature0 WER drops substantially below 0.97,
   that's evidence temperature is a major noise source and worth fixing in
   production before any further tool-vs-tool comparison is meaningful.
3. If it stays high (as the existing 1252 baseline0-vs-temperature0 result,
   WER 0.82, suggests is plausible even at `temperature=0` — see "Hypothesis"
   above), that points toward non-determinism baseline0 can't fully escape
   via temperature alone (consistent with `asl-eval/README.md`'s existing
   note that "Gemini decoding is non-deterministic even at temperature=0 in
   practice"), and the more useful next spend becomes a **human-verified**
   reference for one of 1466/1467/1477/1474 — the only way to learn whether
   SignCaption or baseline0 (at either temperature) is closer to the actual
   signing, which no amount of tool-vs-tool comparison can establish on its
   own.

This experiment spends Gemini API credits, not SignCaption credits, and
reuses infrastructure that is already built, gated, and documented — no new
runner code is needed.
