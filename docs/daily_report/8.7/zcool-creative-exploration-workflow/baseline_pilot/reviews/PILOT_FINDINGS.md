# Pilot Findings

结论先行——本报告的结论分三个独立维度，不要合并成一个词读：

```text
研究阶段本身：       PILOT_COMPLETE_WITH_IMAGE_ACCESS_BLOCKER   （已完成，阻塞点已定位清楚）
抓取规模决策：       SCALE_UP_SCRAPING: PAUSED                   （暂不扩大到20/50案例）
技术阻塞处理：       IMAGE_ACCESS_VALIDATION: CONTINUE            （建议继续验证图片获取方案）
```

也就是说：**小样本研究本身已经做完，不是半途而废；"暂不扩大抓取规模"只针对"要不要现在就去抓20-50个案例"这一件事，不代表整个方向被否定；同时报告明确建议继续推进图片访问方案的验证**。三者分别对应第4-5节的具体理由。

---

## 1. 站酷案例能否用于反向构建设计工作流？

### 可以提取什么
- **案例层元数据**（标题、作者、行业、项目背景）：本 Pilot 5 个案例全部成功提取，质量稳定。
- **部分阶段的文字过程证据**：当页面正文明确采用"阶段化叙述"写法时（如 case_001 的"调研—优势—命名—...—传播"），可以提取出带 `explicit` 证据、`step_order` 和 `order_basis=explicit_text_sequence` 的高质量步骤记录。
- **跨阶段依赖关系**（部分）：case_002 中"包装模块被复用为传播立牌"这类依赖关系可以从正文动作描述中提取，写入 `next_step_dependencies`/`input_assets`。
- **候选案例的初步质量分级**：`workflow_completeness`（complete/substantial/partial/showcase_only/unusable）这一分级在 5 个案例上区分度良好，5 个案例分别落在 substantial（×2）、partial（×2）、showcase_only（×1），说明该分级标准是可执行、可复现的。

### 不可以可靠提取什么
- **任何视觉层证据（`evidence_type=visual_explicit`）**：本 Pilot 中**没有一条记录**使用该证据类型，因为全部 8 个页面的图片都返回占位符（详见 `logs/access_log.md`），不是站酷设限，而是当前工具链（WebFetch）拿不到该站点懒加载后的真实图片。
- **Logo 推导过程**：5 个案例中**没有一个**提供了 Logo 草图/多方案对比的文字或可验证的视觉证据，即使案例标题包含"logo"字样（如 cand_003/cand_005）。这是所有候选中最一致的缺失模式。
- **色彩系统、字体规范的具体呈现**：只有 case_001 有一条关于配色逻辑的文字说明（青草绿+暖橙），其余案例的色彩/字体信息完全依赖图片，而图片不可得。
- **真实创作时间顺序**：即使正文给出了顺序（如 case_001），也只能定为 `order_confidence=medium`——页面叙述顺序不等于真实工作顺序，这是清洗规则明确规定不能自动升级的一点。

### 哪些字段稳定
`case_id`/`source_url`/`source_title`/`source_author`/`industry`/`design_category`/`case_summary` 这些案例层字段，在 5 个案例上提取一致、无歧义，可视为"稳定字段"。

### 哪些字段不稳定
`step.stage_type` 的判定在"服务类别标签"（如"标志/VIS识别/产品包装"）和"真实过程阶段"之间容易混淆——case_003/case_004 的经验表明，一个服务类别名称本身会被误判为"过程被记录了"，实际上只是"交付物类别被列出"。本 Pilot 通过引入 `quality_flags: service_category_label_only_no_process_narrative` 和更低的 `confidence` 来区分，但这需要每次都靠人工/规则谨慎判断，不稳定、不能完全自动化。

## 2. 最适合的数据类型

基于 5 个案例的实测对比（见 `case_quality_review.csv`），价值排序：

1. **带正文明确阶段顺序标签的品牌全案**（如 case_001）——价值最高，因为顺序证据等级可以达到 `explicit_text_sequence`，这是其他类型都达不到的。
2. **带正文策略/结构说明、但无显式顺序标签的品牌全案**（如 case_002）——次高，文字覆盖率可以很高，但顺序只能靠展示顺序推断。
3. **只有最终 Mockup 的案例**——价值最低，即负面样本 case_005 所代表的类型，应在筛选阶段就排除，不必进入详细分析。
4. **带品牌规范页的案例**——本 Pilot 未遇到真正的规范手册页面（`brand_guidelines` 阶段在 5 个案例中全部缺失），无法评估，是未来样本扩大时应重点寻找的类型。
5. **包含多个候选方案的案例**——本 Pilot 同样未遇到（`candidate_outputs`/`selection_reason` 字段在 5 个案例中几乎全部为空），是当前样本的明显盲区。

**结论**：最有价值的不是"图片最多"或"品牌听起来最完整"的案例，而是**正文写作方式本身就是"过程叙事"而非"服务清单"的案例**——这是一个内容写作风格的问题，不完全等同于设计过程本身是否丰富，筛选时需要专门识别这种写作模式。

---

## 3. 自动化和人工分工

### 自动化适合
- 页面元数据提取（标题/作者/发布时间/URL）——本 Pilot 5/5 案例全部自动提取成功；
- 正文初步清洗（过滤导航/评论/互动数据）——WebFetch 的 HTML→Markdown 转换已经完成了大部分工作；
- 完全重复检测（若图片可得，SHA-256）——规则已定义（`CLEANING_RULES_V0.1.md` 第5节），本 Pilot 未落地（无图片字节）；
- 候选阶段初步分类（基于关键词/正文相邻关系猜测 `stage_type`）——可行但**必须**保留人工复核标记，本 Pilot 中已演示（`quality_flags` 字段）；
- JSON/JSONL 格式校验——本 Pilot 已用内联 Python 脚本验证通过（见第十三节质量验证）。

### 人工必须负责
- 判断"服务类别标签" vs "真实过程记录"的区分（case_003/case_004 的核心教训）；
- 判断步骤顺序是否等于创作顺序（`order_confidence` 的最终把关）；
- 判断候选方案与最终选择（本 Pilot 样本中该信息普遍缺失，一旦出现必须人工确认，不能靠正则/关键词匹配）；
- 判断修改关系（`revision_instruction`）；
- 解决数据不一致问题——如 case_001 的品牌名"冯老大/冯老二"矛盾，必须人工回读原页面才能澄清，AI 摘要环节无法自行判断哪个是笔误；
- 判断版权/复用风险，逐案例确认。

## 4. 后续规模建议

```text
SCALE_UP_SCRAPING: PAUSED
```

**这一条只回答"要不要现在把抓取规模扩大到20或50个案例"，不是"这个方向还值不值得做"。** 是否继续解决图片获取问题是独立的第二个问题，答案是继续（见第5节第1条）。

**暂停扩大规模的理由**（不是"数据不好看"式的模糊判断，而是具体阻塞项）：

1. **图片访问是硬阻塞，且是结构性问题，不是本次运气不好**。本 Pilot 访问的全部 8 个页面，图片资源无一例外返回同一占位符 URL。这不是个别页面反爬，而是站酷前端统一的懒加载机制，意味着**扩大到 20 或 50 个案例，图片不可得的比例大概率还是接近 100%**——规模扩大不会稀释这个问题，只会等比例放大"有文字、无图片"的半成品数据量。而设计工作流数据的核心证据（色卡、Logo 网格、字体规范、包装应用）本质上是视觉信息，缺了图片，`visual_explicit` 这一整个证据类型形同虚设。
2. **即使文字质量好的案例，也远未达到 `complete` 等级**。5 个案例里最好的两个（case_001、case_002）都只到 `substantial`，且都缺 Logo 推导、字体规范、品牌规范手册这几类关键阶段。
3. **"背景写得好"不等于"过程记录完整"，容易误判**——case_003/case_004 证明了这一点，如果不做人工复核直接扩量，很可能抓回大量"看起来是品牌全案、实际只是服务清单"的低价值数据。

**在图片访问问题解决之前，不建议投入 20 案例甚至 50 案例的抓取成本**，因为当前最大的价值瓶颈不在样本量，而在**单个页面能拿到的证据类型不完整**。

---

## 5. 下一阶段建议

```text
IMAGE_ACCESS_VALIDATION: CONTINUE
```

本 Pilot **不建议现在就进入 20/50 案例阶段（见第4节），但明确建议继续往下推进图片访问问题的验证**，这不是"停下来"，而是"换一个更小、更聚焦的下一步"。为避免此次工作被浪费，下一步的最小方案是：

1. **优先解决图片获取问题**，而不是急着扩样本。可选路径（均需要用户/团队决策，本 Pilot 不擅自尝试）：
   - 引入浏览器自动化/截图工具（如 headless browser）实际渲染页面后再截取图片区域；
   - 人工下载 3-5 张关键图片作为"图片可得后效果如何"的小规模验证，先看看投入产出比再决定是否规模化；
   - 评估是否有官方/授权的数据获取方式，避免任何形式的规避限制。
2. **若图片问题解决**，建议先用**同样的 5 个案例**（case_001~case_005）重新跑一遍完整流程（补上 `visual_explicit` 证据、图片切分、去重），而不是立刻换新案例——这样可以直接对比"有图 vs 无图"对数据完整度的实际影响幅度，作为是否值得 20 案例 Pilot 的量化依据。
3. **目标案例数（若图片问题解决且上述验证通过）**：建议下一轮先做 **10 个案例**（而非直接 20），且要求至少 6 个来自"有明确阶段顺序标签"这一类型（对照本 Pilot 第2节的价值排序）。
4. **筛选条件**：优先选择正文本身是"过程叙事"写法的案例，用第2节总结的模式识别方法预筛，避免重复本 Pilot 中"背景好但过程空"的误判成本。
5. **自动抓取范围**：仅限元数据+正文+图片下载（若技术方案确定），不做自动化的 `stage_type` 最终判定，只做初步候选建议。
6. **人工复核流程**：每个案例至少过一遍第3节列出的"人工必须负责"清单，尤其是顺序可信度和服务类别标签识别。
7. **数据质量门槛**：`workflow_completeness` 低于 `partial` 的案例（即 `showcase_only`/`unusable`）应在筛选阶段就排除，不进入详细提取，参考本 Pilot 对 cand_001/cand_004/cand_005 的处理方式。
8. **是否需要独立抓取脚本**：需要，但应等图片获取方案确定后再开发，避免脚本返工。
9. **是否需要图片切分**：需要（长图/组合图在 case_003/case_004 的高图片数量案例中大概率存在），规则已在 `CLEANING_RULES_V0.1.md` 第3-4节预先定义，可直接复用。
10. **是否需要视觉模型辅助**：是，图片可得后建议引入视觉模型判断 `detected_content`/`workflow_stage_candidates`，但仍需人工抽检，不能全自动信任。
11. **是否需要与 Brand Direction Explorer 对接**：本轮不涉及，按任务要求本 Pilot 未修改、未评估该模块，是否对接应在图片问题解决、且有更大样本验证工作流数据实际有用后再单独决策。
