# Access Log — 站酷 (ZCOOL) Pilot

本日志记录本次 Pilot 中对站酷页面的全部访问尝试。所有访问均通过 Claude Code 内置的 `WebSearch`（发现候选 URL）和 `WebFetch`（读取单个页面、转换为 Markdown 并做只读文本分析）工具完成。未使用浏览器自动化、未使用账号登录、未使用高频请求、未尝试绕过任何访问限制。

## 环境与方式说明

- 可用方式：`WebSearch`（站内/站外搜索发现 URL）、`WebFetch`（对给定 URL 发起只读抓取，内部将 HTML 转换为 Markdown 后交由小模型做摘要提取）。
- 不可用/未使用：无浏览器渲染工具、无 `curl` 直连测试（环境中 `curl` 可用，但站酷图片资源通过 JS 动态加载 + 防盗链机制提供，直接 `curl` 静态 HTML 同样无法获得真实图片，与 WebFetch 结果一致，因此未重复验证以避免不必要的重复请求）。
- 请求频率：本 Pilot 全程对 zcool.com.cn 的直接页面访问共 8 次（1 次每个候选 URL），均为单次访问，无重试、无轮询、无并发爆破。

## 关键发现：图片资源无法通过当前工具获取真实内容

**所有 8 个页面的图片均返回占位符**，实际图片 URL 表现为：
`https://public-static.zcool.com.cn/git_z/z/images/new/bg-placeholder.jpg`

这说明站酷的作品图片走的是前端懒加载/JS渲染填充机制（真实图片 src 由客户端 JS 在滚动或页面加载后动态替换），静态抓取（WebFetch 的 HTML→Markdown 转换）拿到的是加载前的占位符，而不是真实设计图。这不是访问权限问题（没有登录墙、没有验证码提示），而是**渲染管线限制**。

**影响**：本 Pilot 中所有案例的图片层数据（`asset_manifest.csv` 中的图片行）只能记录远程页面 URL、页面中出现的图片位置/说明文字（如有），无法记录真实图片内容、无法做视觉判断（如"是否是色卡""是否是logo草图"），除非后续引入浏览器截图或人工下载。这一点在每个案例的 `REVIEW.md` 和 `PILOT_FINDINGS.md` 中均如实注明，未编造任何图片内容判断。

正文文字内容（标题、作者、项目背景、设计说明段落）可以正常通过 WebFetch 获取，来源于页面真实渲染的服务端 HTML，不受此限制影响。

## 未尝试/未使用的方式

- 未尝试登录站酷账号；
- 未尝试绕过验证码；
- 未使用非官方 API 或逆向接口；
- 未抓取评论区用户信息；
- 未对同一 URL 重复请求；

## 结论

当前工具链（WebSearch + WebFetch）足以支撑**文字层面**的案例筛选与内容清洗规则验证，但**不足以支撑图片层面**的真实内容抓取与视觉判断。这是 Pilot 阶段必须如实报告给老板的关键限制，直接影响"是否值得扩大到 20–50 个案例"的判断——在图片抓取问题解决之前，扩大规模只会成比例放大"有文字、无图片证据"的半成品数据。
