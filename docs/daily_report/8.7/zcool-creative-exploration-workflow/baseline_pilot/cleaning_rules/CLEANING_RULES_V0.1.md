# Cleaning Rules v0.1 (Pilot)

适用范围：站酷品牌设计案例页面 → `design_workflow_schema_v0.1.json` 结构化数据。本版规则基于对 8 个真实候选页面（含 5 个详细案例）的实际观察制定，不是纯理论设计。

---

## 1. 正文清洗

**保留**：项目背景、客户/品牌需求、设计目标、用户或市场信息、品牌定位、创意理念、设计推导、色彩说明、Logo 说明、字体说明、包装和应用说明、方案选择或修改说明。

**排除**：站酷导航、推荐作品、评论区、点赞收藏数、关注按钮、作者自我推广、联系方式、页脚、平台广告、重复文案、与设计过程无关的版权声明。

**实践观察**：本 Pilot 中 WebFetch 返回的 Markdown 已经在转换层面过滤掉了大部分导航/广告噪音，真正需要人工/规则清洗的主要是：(a) 作品浏览量/分享数/举报数等互动统计（如 cand_005 页面出现"20068次浏览、193次分享、128次举报"），(b) 设计团队署名与工作室推广语（如 cand_008 的"设计总监令语..."属于团队信息，应归入 case 层元数据而非 step 层正文），(c) 平台通用免责声明（"图片已存证，版权保护中"这类提示是站酷平台功能提示，不是设计说明，需排除出正文但可保留在 asset 层作为水印/存证状态标记）。

版权/来源声明单独保留在 `case.copyright_or_reuse_notes`，不得混入 `step.evidence_text` 或 `step.output_description`。

---

## 2. 图片清洗

**保留**：Brief/策略图、Moodboard、草图、Logo 候选方案、Logo 网格/推导、色卡、字体规范、辅助图形、包装设计、物料设计、门店/空间应用、品牌规范页。

**降级或排除**：重复 Mockup、同图不同尺寸、页面缩略图、纯装饰图、无法识别的极低分辨率图片、无关推荐图、作者头像、平台 UI 截图、评论区图片。

**Pilot 阶段的现实限制**：由于本轮全部图片均以 `bg-placeholder.jpg` 占位返回（见 `logs/access_log.md`），**图片清洗规则在本 Pilot 中无法真正执行**，只能基于页面文字上下文（图片前后的说明文字、图片在页面中的相对位置）做初步分类假设，并在 `asset.quality_flags` 中统一标记 `image_bytes_unavailable`。任何"这张图是色卡"之类的判断，只有当页面正文明确点名（如"色彩系统如下"紧邻的图片）时才可标注，且 `evidence_type` 只能是 `explicit`（对应文字段落）而不能是 `visual_explicit`（因为没有真正看到图片）。

---

## 3. 长图处理

**规则（本 Pilot 未实际执行切图，因为没有真实图片字节，以下是可执行的规则定义，供后续阶段落地）**：

- 是否保留原始长图：**是**，`asset_type=image` 的原图始终保留一条完整记录，`local_path`/`source_url` 指向原图。
- 是否按视觉段落切分：仅当原图确认为"长图"（高宽比超过约 3:1，或页面本身用分隔线/编号标出多个段落）时才切分；普通单一场景图不切。
- 切分后的 panel 编号：使用 `panel_index`（从 0 开始，按从上到下顺序），记录在独立的 `long_image_panel` 结构中，`original_asset_id` 指回原图。
- panel 如何映射到原图：通过 `original_asset_id` + `panel_bbox`（像素坐标 x/y/width/height）双重映射，保证可追溯回原图任意矩形区域。
- 是否需要保存坐标顺序：需要，`panel_bbox` 必填其一（坐标或明确的"未切分，仅记录顺序"标记）。
- 避免切断文字/设计元素：切分前需先做视觉分段检测（如空白间隔/背景色变化），不得按固定像素高度机械切割；宁可少切、保留稍大 panel，也不要切断色卡编号或字体样本。
- 一张长图包含多个阶段时：在 `panel_stage_candidates` 中允许多值，并保留整图的 `is_composite=true` 标记作为兜底。

---

## 4. 组合图处理

一张图同时包含 Logo、色卡、字体和包装时：

- 标记 `asset.is_composite = true`；
- 不强行只归到一个 `stage_type`；
- `workflow_stage_candidates` 允许记录多个候选阶段；
- 若长图切分规则（第3节）可以稳定切分，则拆成多个 `long_image_panel`；
- 若不能稳定切分（如设计师在一张自由排版的展示页里混排了多种元素，没有清晰视觉分隔），则**保留整图**，在 `step` 层的 `evidence_asset_ids` 中让多个 step 共同引用同一个 `asset_id`，并在每个 step 的 `review_notes` 中注明"该证据图为组合图的一部分，需人工复核以确认归属"。

本 Pilot 观察：cand_007（MELLOWCO，40+ 张图）和 cand_008（韬客直播基地，30+ 张图）的图片数量远超案例的文字阶段数，高概率存在组合展示页（品牌规范手册常见排版方式），但由于图片不可见，本 Pilot 无法验证，已在对应案例的 `REVIEW.md` 中标记为"待人工确认是否存在组合图"。

## 5. 重复图处理

**定义**：
- 完全相同文件（同一份图片字节，可能不同文件名）；
- 不同尺寸的相同图片（如缩略图 vs 原图）；
- 裁切版本（同一构图的局部）；
- 加水印版本（同一图片的水印/无水印两个版本）；
- 同一 Mockup 的轻微变体（如同一杯型换个摆放角度）；
- 同一设计在不同背景下的展示（如同一 Logo 分别放在白底和场景图里）。

**处理原则**：
- 完全相同文件 → 应删除，只保留一条记录，其余记为 `is_duplicate=true` 并归入同一 `duplicate_group`；
- 不同尺寸/裁切/水印版本 → 不删除，归入同一 `duplicate_group`，但保留各自记录，因为水印状态、裁切范围本身是有效元数据（例如无水印版本可能更适合作为分析素材）；
- 同一设计的不同展示场景（不同背景/角度）→ **视为独立信息**，不归为重复，因为角度/场景本身可能对应不同的 `workflow_stage_candidates`（如同一 Logo 出现在"Logo 系统"页和"门店应用"页，属于两个阶段的证据，不是重复）。

**哈希方案**：完全重复用 SHA-256；近似重复（裁切/轻微变体）用 perceptual hash（如 pHash）。**但哈希结果只作为 `quality_flags` 中的提示（如 `possible_duplicate_phash`），不自动删除记录**，必须保留 `is_duplicate` 字段供人工复核后再确认，避免哈希误判（例如两张视觉上相似但实际是不同色号色卡的图片）删掉有效数据。

本 Pilot 未做哈希检测（无图片字节可用），此规则待后续阶段图片下载后落地。

## 6. 设计过程与最终展示的区分

`is_process_asset` 覆盖：草图、研究、推导、网格、候选方案、方案对比、设计规范、修改前后对照。

`is_final_showcase` 覆盖：完成后的包装 Mockup、门店效果图、海报效果图、产品摄影式展示、品牌全景展示。

一张图可同时为二者（例如"修改前后对照图"右侧是最终成品，左侧是过程草稿），此时需在该 asset 关联的 `step.review_notes` 中写明原因，不能只打两个布尔值了事。

**Pilot 观察**：5 个详细案例中，只有 `case_006`（冯老二散养牛）的正文明确区分了过程性内容（调研、命名推导、记忆符号设计）和展示性内容（传播物料展示），其余案例（`case_002`/`case_007`/`case_008`）的正文更偏"设计说明文案"而非"过程记录"，图片本身又不可见，因此这三个案例中"哪些图是过程图、哪些是最终展示图"**目前无法可靠判断，只能标记为 `unknown`**，不能靠猜测填充。`case_003`（视觉盛宴，负面样本）则明确 100% 为 `is_final_showcase`，没有任何过程证据——这正是负面样本存在的意义：验证清洗规则能正确识别出"只有成品"的案例并如实标注,而不是勉强凑出几个虚假的 process 步骤。

## 7. 步骤顺序

**证据优先级**（从高到低）：
1. 页面正文明确写出的顺序（`order_basis=explicit_text_sequence`）——如 `case_006` 正文直接给出"调研—优势—命名—购买理由—记忆符号—差异化—设计—传播"；
2. 页面从上到下的展示顺序（`order_basis=page_visual_top_to_bottom_order`）；
3. 图片上的编号或章节标题（`order_basis=image_numbering_or_heading`）；
4. 设计逻辑上的依赖关系（`order_basis=design_logic_dependency`，如"色彩系统一定早于包装应用"这类不需要页面证据也能成立的强逻辑约束）；
5. 人工推断（`order_basis=manual_inference`）。

**关键规则**：若某案例只有第 2 级证据（页面展示顺序），**不能自动等同于真实创作顺序**——设计师撰写案例展示页时，完全可能按"讲故事效果"而非"实际工作顺序"排版。此时 `order_confidence` 最高只能定为 `medium`，且需在 `order_basis` 中如实记录为 `page_visual_top_to_bottom_order` 而非更高等级。

必须同时记录 `step_order`（数字）、`order_confidence`、`order_basis` 三个字段，不能只给一个顺序数字。

---

## 8. 缺失步骤

如果案例没有展示市场调研、Brief 或 Logo 草图：

- **不补写不存在的步骤**——即使行业常识告诉我们"做品牌肯定先有调研"，只要页面没写、图片也看不到，就不生成对应的 `step` 记录；
- **不根据行业常识伪造**内容细节；
- 在 `case` 层新增非 schema 强制但推荐记录的 `missing_stages` 备注（写入 `case_summary` 或案例 `REVIEW.md` 的"缺失阶段"小节），列出预期常见但本案例未出现证据的阶段类型；
- 若确有合理推断依据（如"有色彩系统输出，逻辑上必然先有过某种调色过程"），可以生成一条 `evidence_type=inferred` 的 step，但 `confidence` 必须为 `low` 或 `medium`，且 `evidence_text` 中要写明推断依据而非假装是页面原文。

本 Pilot 5 个案例中，`missing_stages` 的典型模式：**几乎所有案例都缺 `logo_sketch`/`logo_exploration`（Logo 草图/多方案对比过程）的文字或视觉证据**，即使案例标题包含"logo"字样；只有 `case_006` 提供了接近该类别的"记忆符号"设计说明，但仍不是严格意义上的 Logo 草图推导。这是本 Pilot 最值得向老板汇报的模式性发现之一。

## 9. 可训练性判断

区分三个独立布尔字段：`usable_for_analysis` / `usable_for_workflow_training` / `usable_as_visual_reference`。三者不是同一件事：

| 字段 | 判定标准 |
|---|---|
| `usable_for_analysis` | 内容真实、来源可追溯、无严重伪造风险，可以被引用来做定性观察（如"发现该行业常缺 Logo 推导证据"），即使数据本身不完整 |
| `usable_for_workflow_training` | 要求 `workflow_completeness` 至少达到 `substantial`，且至少 2 个不同 `stage_type` 的 step 拥有 `evidence_type=explicit` 或 `visual_explicit`，`order_confidence` 至少 `medium`。**图片字节不可得的案例，即使文字证据再好，也不满足训练数据的完整性要求，因为训练数据通常需要图文对应关系，而不仅是文字描述** |
| `usable_as_visual_reference` | 要求图片实际可见（本 Pilot 中因图片全部不可得，**没有一个案例满足此项**），且画面本身具有一定设计完成度 |

**结论**：本 Pilot 全部 5 个案例的 `usable_for_workflow_training` 与 `usable_as_visual_reference` 均为 `false`（前者因完整度不足 `substantial` 的严格标准或图文对应关系缺失，后者因图片完全不可得）；`usable_for_analysis` 中 `case_006`/`case_002` 为 `true`，用于验证 schema 与清洗规则的可执行性，其余为部分可用或不可用。详见 `case_quality_review.csv`。

## 10. 版权与来源

研究仅用于内部分析与数据结构验证，不用于对外发布、不用于模型训练、不重新分发站酷素材。

每个案例必须保留：
- 原始来源平台（`zcool`）与 URL；
- 作者（页面署名，不做推测或补全）；
- 访问日期；
- 水印状态（本 Pilot 因图片不可见，统一记为 `unknown`，不得假设"无水印"）；
- 版权/复用风险说明——统一注明"内容为站酷平台设计师原创作品，版权归原作者/工作室所有，本研究仅做内部数据结构验证，不做二次发布"。

严禁在任何文档中将站酷素材描述为"Curify 自有资产"或暗示 Curify 拥有其版权。
