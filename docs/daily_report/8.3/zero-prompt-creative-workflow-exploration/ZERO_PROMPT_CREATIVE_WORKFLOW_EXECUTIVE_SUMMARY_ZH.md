# Curify 零提示词创意工作流：执行摘要

**文档性质：** 本地研究摘要，供团队快速阅读。完整证据请见同目录下的英文文档（`ZERO_PROMPT_CREATIVE_WORKFLOW_EXPLORATION.md` 及其附件）。本摘要中的所有代码相关结论均为**源码层面**审计结果，**未独立验证生产环境的实际运行状态**（包括是否上线、是否被 feature flag 控制、是否在 A/B 实验中）。

---

## 1. 任务背景

团队怀疑 Curify 当前的产品体验和对外营销（"Images for every query"）可能与用户真实需求存在错位：用户不想学 prompt、只有模糊想法、希望从参考图或简单需求直接拿到专业结果。本任务据此审查了 PR #416（一份零提示词工作流提案）以及 Curify 前后端仓库的现有源码，评估这个怀疑是否有依据，并给出一条可执行的产品/营销路径。

## 2. 核心发现

- PR #416 是一份**已合并、但只包含文档、不含任何代码**的提案（2 个新增 Markdown 文件，0 个代码文件）。它准确诊断了方向性问题，但其中提出的两个交互概念——"Magic Drop" 和 "Visual Mad Libs"——**在检查范围内的前端源码中未找到同名实现**。
- 前端源码中确实存在与担忧直接相关的证据：首页当前有两个入口组件（`HomeOmniInput` 文本路由 和 `HomeImageWorkbench` 上传选工作流），二者代码注释相互矛盾（一个自称会取代另一个），但两者都出现在首页组件组合中。这说明首页入口策略在源码层面**尚未达成一致**——这是一个具体、可在代码中观察到的信号,但不能证明它是所说"整体错位"的唯一或根本原因，是否合并/替代/做 A/B 测试仍需产品团队决策。
- 现有生产环境的真实运行状态（哪个入口实际展示给用户、流量如何分配）**本次审计无法验证**，因为没有运行时/生产环境访问权限。

## 3. 零提示词定义

**"零提示词"不等于用户完全不输入，而是用户只提供目标、参考图或必要事实，不需要学习和编写 AI prompt。** 系统负责把用户的"人话"翻译成生成所需的技术指令；用户永远不需要看到或编辑这个翻译过程。

## 4. 推荐主流程

```
主线（Primary）：
选择要做什么
→ 填写少量必要信息
→ Curify 提供 2–3 个创意方向
→ 用户选择
→ 生成结果

辅助入口（Supporting）：
上传或选择参考图，进入同一条结构化工作流。

兜底路径（Fallback）：
描述一个开放式想法
→ 系统识别可能的目标/方向
→ 路由进入同一条结构化工作流。
```

**重要说明：** 这三条路径不是平级选项。Goal-first 是主线，Reference-first 是辅助入口，Idea-first（开放式）是兜底路径，用于覆盖不在预设目录里的需求。

## 5. 为什么选择 Goal-first

这是**基于当前有限证据和现有能力复用程度得出的工作假设**，而非已被数据验证的结论：

- 源码中已存在一个与 Goal-first 高度相似的构建块（`HomeImageWorkbench`，"选工作流→上传→生成"），说明这条路径的首个验证 Demo 主要是包装和收窄现有能力，而不是从零构建新技术。
- PR #416 引用的是**一轮有限的、以英文 Reddit 为主的需求挖掘样本**（中文/小红书数据明确尚未完成）。在这个有限样本中，卖家/中小商家的"帮我做成套产出"类需求信号相对更直接——这是一个方向性参考,不能代表完整市场结论，但恰好与 Goal-first（选交付物→拿到成套结果）的思路吻合。
- 开放式 Idea-first（不给任何约束，直接理解用户模糊想法）技术风险最高、最难做出稳定质量，更适合作为长期兜底，而非第一步验证对象。

## 6. 当前已有能力（在检查的源码中观察到）

- 搜索、模板浏览和生成路径已经通过共享数据和路由连接在一起；
- 存在结构化参数表单（按模板收集姓名、日期等字段）；
- 存在参考图上传组件，并已接入生成工作台；
- 存在一套基于 LLM 标注的意图分类体系（8 个创意意图簇），目前只用于搜索结果之后的筛选，尚未前置到生成之前；
- 存在两条生成后端路径（结构化模板生成、自由文本 prompt 生成）；
- 存在结果的衍生处理能力（尺寸适配、印刷出血线等），但都是对整张图的处理，不是对内容字段的编辑。

以上均为**源码中观察到的构建块**，不代表这些能力在生产环境中已经完整组合上线并被真实用户使用。

## 7. 当前主要缺口

- 缺少生成前的真实创意方向推荐能力（"给我 3 个方向选"这一步在检查范围内未找到）；
- 首页入口逻辑（两个入口组件）需要产品团队做出明确决策，而不是靠工程默认合并；
- 开放式想法（无明确目标类型）尚未有稳定的路由机制进入结构化工作流；
- 任意参考图（非目录内图片）的自动风格/结构理解仍需开发；
- **字段级编辑（如只改店名和日期，不用重新生成）属于有价值的后续扩展，但不是验证零提示词 P0 假设的必要条件** —— 代码注释中明确将其列为"稍后阶段"，这是一个真实存在的缺口，但本次修订刻意不再把它列为"最大缺口"或 MVP 必需项，避免它拖累或混淆 P0/P1 的验证节奏。

## 8. P0 Demo

**场景：咖啡店开业海报**

```
用户选择"海报"
→ 输入店名和日期
→ 展示三个预置创意方向
→ 选择一个
→ 接入当前源码中的生成路径，并在拍摄前完成运行验证
→ 导出
```

明确要求：
- 三个方向在 P0 阶段**必须是人工预置/为该场景手工挑选**，不能假装存在一个通用的、可泛化的方向推荐模型；
- **不在当前对外宣传中演示尚未实现的实时字段编辑**（改日期、改店名）——这属于 P1 扩展，应清楚标注为"未来目标"，绝不能作为当前产品能力发布。

## 9. P1 / P2

- **P1 核心：** 真实的方向推荐服务、扩展交付物目录、首页两个入口的产品决策与统一、完整的失败恢复流程。
- **P1 扩展：** 字段级内容修改（无需重新输入 prompt），需要后端项目数据结构支持，属于独立的后续工作，不与 P0/P1 核心验证节奏绑定。
- **P2：** 任意参考图的自动理解、开放式想法的稳定路由、基于历史记录的个性化。

本文档未给出任何具体开发工时估算，因为目前没有足够依据支撑精确的工时判断。
