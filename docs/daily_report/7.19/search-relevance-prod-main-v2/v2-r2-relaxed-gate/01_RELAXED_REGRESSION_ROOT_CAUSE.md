# V2-R2 Stage: Root-Cause Analysis of the V2-R1 326-Set Regression (50 queries)

Date: 2026-07-19. V2-R2 worktree: `/Users/baobaoli/Desktop/curify-frontend-search-v2-r2-2026-07-19`, branch `baobao/search-relevance-prod-main-v2-r2-2026-07-19`, initial SHA `32f6282a240edfa87edae5a0ba5308aecf462466` (identical to V2-R1 frozen).

## 0. What this document is, and is not

This is a re-verification of the V2-R1 report's claim ("移除二元 `hasStrict` 门禁后，弱 relaxed 候选稀释了原本纯净的 strict-only 结果集") against **live, code-level, per-candidate evidence**, not just the aggregate label/score numbers in `32_REGRESSION_AND_IMPROVEMENT_CASEBOOK.csv`. The conclusion below **does not match** the V2-R1 report's framing, and this document explains why, with reproducible evidence.

## 1. Method

The V2-R1/V2-R2 codebase (`app/[locale]/(public)/search/page.tsx`) has no built-in way to inspect `isOriginal`, source path, or per-candidate score breakdown for a live query — the RSC payload only exposes final titles. To get real per-candidate evidence (not just re-reading the aggregate CSVs), a temporary, env-var-gated debug trace (`SEARCH_DEBUG_TRACE=1`) was added to **V2-R2 only** (never to V2-R1), immediately after `finalSelected` is computed, logging to stderr: `id`, `title`, `templateId`, `isOriginal`, `sourcePaths` (`original` / `rewrite:<text>` / `decomposition:<slot>`), `pathHits`, and the full `ScoreBreakdown` (all weight components + `reasons`) for the top 15 finally-selected candidates. V2-R2 was `npm install`ed, its `.env.local` copied (content only, never printed) from the V2-R1 worktree, and run via `next dev` on a private port (4601). All 50 queries flagged `regressed=true` in `eval_raw/EASY326_PAIRED.csv` were queried against this instrumented server; the raw trace (`all_traces.jsonl`, 50 lines) backs every row in `02_REGRESSED_QUERY_RELAXED_TRACE.csv`.

This is a **live re-verification run**, days after the original V2-R1 326-eval, so exact top-5 titles can differ from the historical `EASY326_V2.csv` row for queries that depend on the non-deterministic LLM rewriter (already a disclosed limitation in `31_STATISTICAL_COMPARISON.md` — see `teddy bear` below for a concrete recurrence). The **code-structural findings** (which mechanism admitted which candidate, whether it is floor-protected) are deterministic and do not depend on which specific rewrite phrasing fired.

The debug instrumentation is temporary and has been reverted before this stage concludes; it does not appear in any commit.

## 2. The two admission mechanisms that actually exist in the code

Reading `lib/relevanceScorer.ts` + `page.tsx` (lines ~630-991) shows the pipeline has **two structurally different populations**, and the V2-R1 report's "strict/relaxed" framing conflates them:

**(a) `isOriginal` / "original-floor" candidates** — `originalIds = baseResult.scored` (the result of scoring the user's literal query, including **template-level strict promotion**: once a template's full blob — title, category, tags, topics, *and free-text description* — strict-matches the query anywhere, **every inspiration under that template** is promoted to a synthetic `score=100` "strict" record, with `tagsHit` and `substringOnly:false` **hardcoded**, regardless of whether that specific inspiration has anything to do with the query). `selectFinalCandidates` guarantees every `isOriginal` record survives **unconditionally** — this is the Direction-1 "existence floor" invariant, which this stage is explicitly forbidden from touching ("不破坏方向1、2、6").

**(b) non-original ("relaxed") candidates** — records that only came from a rewrite or decomposition path. These are gated by `MIN_SCORE_WHEN_ORIGINAL_NONEMPTY = -5` (when `originalIds` is non-empty) or by `MIN_SCORE_WHEN_ORIGINAL_EMPTY = -5` **with a never-zero override** (`MIN_KEPT_WHEN_ORIGINAL_EMPTY = 5`: if fewer than 5 candidates clear the floor, the top 5 by score are kept **regardless of the floor**) when `originalIds` is empty.

**A Strict/Relaxed admission gate can only ever affect population (b).** Population (a) is immune to any such gate by design (that is the whole point of the Direction-1 invariant), and the never-zero override inside (b) makes a *subset* of (b) also immune (you cannot exclude a below-floor candidate that the never-zero rule is forcing in, without either raising the never-zero minimum below the pool size — a new zero/near-zero-result risk — or improving the candidate pool itself, which is out of scope this round).

| Classification | Count | Fixable by a Strict/Relaxed admission gate this round? |

| `ORIGINAL_TEMPLATE_OVERPROMOTION` | 22 (44%) | **No** — every offending candidate is `isOriginal:true`, protected by the Direction-1 floor. The defect is in the ORIGINAL query's own template-level strict promotion, not in relaxed/rewrite admission. |
| `RELAXED_SCORE_TOO_HIGH_SENSE_COLLISION` | 18 (36%) | **No** — offending candidates are non-original but already score well above the -5 floor (15 to 50) via genuine whole-token/tag hits on the *wrong sense* of an ambiguous word (e.g. "banner" → Marvel's Bruce **Banner**; "tag" → metadata tag, not clothing tag; "figure" → historical-figure infographics). | `WEAK_RELAXED_DILUTION_PARTIAL` | 5 (10%) | **Yes, partially** — some relaxed candidates clear the quality floor, others are pure never-zero padding below it. This is the only bucket a minimal Strict/Relaxed gate can meaningfully touch. |
| `CATALOG_GAP_NEVER_ZERO_FLOOR` | 5 (10%) | **No** — 100% of available candidates already score below the floor; they are kept only because the never-zero guarantee (`MIN_KEPT_WHEN_ORIGINAL_EMPTY=5`) refuses to return fewer than 5 (or fewer than the whole pool, if the pool has ≤5 records) when nothing clears the floor. ## 5. Direct answers to the 5 mandatory questions

1. **How many of the 50 regressions are directly Relaxed-related** (i.e., a non-original candidate whose admission is actually governed by a tunable floor/count, where tightening that gate would change the outcome without violating the never-zero/original-floor invariants)? **5 of 50 (10%)** — the `WEAK_RELAXED_DILUTION_PARTIAL` bucket (手办, 娃娃, 挂件, 酒标, online store banner). Even these are only partially fixable (some low-quality padding is structurally required by the never-zero rule).
2. **How many are NOT a Relaxed problem?** **45 of 50 (90%)** — 22 are `ORIGINAL_TEMPLATE_OVERPROMOTION` (floor-protected, non-original mechanism doesn't even apply), 18 are `RELAXED_SCORE_TOO_HIGH_SENSE_COLLISION` (non-original but already comfortably above any reasonable floor via a genuine-but-wrong-sense match), 5 are `CATALOG_GAP_NEVER_ZERO_FLOOR` (100% below floor, but that's every candidate that exists — nothing to exclude in favor of).
3. **Is weak-Relaxed dilution really the main root cause?** **No.** It explains at most 10% of the 50 regressions, and even that 10% only partially. The dominant mechanism (44%) is template-level strict promotion on the **original** query pass — a different defect, in a different part of the pipeline, explicitly protected by the Direction-1 invariant this stage must not break. The second-largest mechanism (36%) is lexical/sense collision on genuinely-scored candidates, which a quality-floor or count-cap gate cannot address without also stripping legitimately relevant content.
4. **Which queries can't be solved by this round's fix?** All `ORIGINAL_TEMPLATE_OVERPROMOTION` (22), all `RELAXED_SCORE_TOO_HIGH_SENSE_COLLISION` (18), and all `CATALOG_GAP_NEVER_ZERO_FLOOR` (5) — 45 of 50, including 3 of the 5 mandated focus queries (`figure`, `doll`, `teddy bear`/`泰迪熊`).
5. **Is there a smaller fix than adding complex rules?** For the one real bucket (`WEAK_RELAXED_DILUTION_PARTIAL`, 5 queries), yes — see the alternative considered in §6. But building it does not move the needle on the other 90%, and cannot make the 326-set net-negative result (50 regressed > 36 improved) flip to net-positive, because the two dominant mechanisms are untouched by construction.

## 6. Conclusion

The evidence does not confirm that "弱 Relaxed 候选稀释" is the primary root cause of the V2-R1 326-set regression. It is a real, minority (~10%) contributor. The majority (90%) of the 50 regressed queries are caused by (a) template-level strict-match over-promotion on the **original** query pass — protected by the Direction-1 floor this stage is required to preserve — and (b) genuine lexical/sense collisions that score well above any floor a Relaxed gate could reasonably set.

Per this stage's charter (§5): **a Relaxed Gate will not be implemented.** Building one would touch only 5 of the 50 regressed queries, partially, while leaving the two dominant mechanisms — and therefore the 326-set net-negative outcome — unchanged. Implementing it anyway would not be a "minimal, evidenced fix"; it would be a gate built to a hypothesis the data does not support, which the task explicitly instructs against ("不要机械实现...只选择满足以下条件的最小机制...能直接解释已确认回归").

No code changes have been made to V2-R2 (the temporary debug trace has been reverted). No calibration set, config lock, or scorer changes were implemented, per §5's explicit instruction to stop here when root cause is not confirmed.
