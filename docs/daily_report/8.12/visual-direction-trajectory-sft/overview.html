01

What gc-minimal-zine-poster actually offers

A public Codex Skill (markdown instructions, no code, no logged runs) for generating minimal zine posters. It has no executed trajectories to learn from — but its documented procedure gives a working vocabulary for stage design. Full detail in REPO_ANALYSIS.md.

Adopt the pattern

Fixed / variable / residue split. Reference analysis separates traits that must carry over, traits safe to vary, and sample-specific detail that must never be reused.

Adopt the pattern

Numeric, checkable fields over adjectives. "70–90% negative space" can be graded; "elegant" cannot. Curify needs its own domain-specific numbers, not the poster repo's.

Adopt the pattern

Anti-repetition rule on variation. New candidates must change layout grammar, not just position — directly informs the direction-diversity benchmark dimension.

Adopt the pattern

Capped single-retry revision. Regenerate once against a stated defect; if still failing, disclose the limitation rather than claim success.

Do not copy

The poster-specific numbers. 3:5 canvas, one high-chroma hue at 0.8–2.5% area — tuned to one visual family, not transferable to coffee/brand/packaging.

Do not copy

The eval set as "a benchmark." evals.json is seven rubric prompts for a human/LLM reader — no automated metrics, no step-level breakdown. Evidence that lightweight rubrics work as one layer, not proof of rigor.

02

What the manager-provided discussion adds

A ChatGPT discussion shared by the manager — inaccessible to automated fetch in the first pass, later provided as transcript text and now incorporated (see footer note). Full source-attributed analysis in DISCUSSION_ANALYSIS.md.

Core thesis

Distill behavior, not hidden CoT. For an agent product, the useful target is trajectory, tool-use policy, taste, and recovery behavior — not an unrestricted reasoning trace.

Reframe

"100k decisions," not "100k images." The valuable asset may be decisions about what changes next in a design state, not a media library.

New data pattern

BEFORE → CLIENT FEEDBACK → AFTER. "This feels too cheap" → concrete design changes → "This is right." Turns qualitative feedback into observable actions.

Caveat

Interface memorization risk. Trajectory SFT on one fixed tool schema may teach token-matching, not tool-use semantics — needs deliberate perturbation testing.

Caveat

Teacher-data compliance. Don't assume a closed frontier model's output can freely train a competing model — verify terms before any real distillation run.

Strategic

Product niche hypothesis. Brief → Design System → Product Family → Production, not "generic Design Agent" — recorded as a hypothesis, not a commitment.

03

Workflow data vs. trajectory data

Curify's 8.8 workflow research (five domains) captured finished-project case studies — a content pipeline. Trajectory SFT needs a different object: a logged decision process, including paths that were tried and rejected.

Workflow data — what shipped

brief
↓
concepts
↓
design
↓
final result

Linear. One path. No rejected candidates — a published case study cannot show what didn't ship. Source: cases/brand_logo_001/workflow_extraction.json and similar.

Trajectory data — how it was decided

state
↓
decision → action / tool
↓
observation → evaluation
↓
revision (if needed)
↓
final output

Branches. Includes rejected candidates and their stated reasons. This is what SFT on decision-making requires.

04

Three layers: harness, trajectory, preference

The discussion's data model. Harness is designed and logged first, before any model training; trajectory data trains next-action policy; preference data trains taste — three different objects, never collapsed into one dataset.

1 · Harness

Workflow + tools, designed first. Brief → find references → propose directions → generate → inspect → detect problems → adjust → regenerate → expand to more assets.

2 · Trajectory

Action-policy SFT. state + tools + history → next action/tool/arguments/decision. Expert trajectories, not hidden reasoning traces.

3 · Preference

Taste as comparison. Pairwise judgments ("A > C") from a model judge, designer, client, or user behavior — reward/judge models, DPO, reranking, self-critique.

05

Proposed Curify trajectory stages

Ten core stages, derived from the 8.8 workflow vocabulary, the poster repo's procedure, and the requirement that a weak direction be catchable mid-trajectory — plus one new conditional stage from the manager-provided discussion. Three stages are conditional; most trajectories skip them when the first direction already clears the bar.

01Brief understanding

Parse the brief into mood, constraints, format — explicit and checkable, not implied.

02Reference retrieval

Select or fetch reference material relevant to the brief.

03Reference analysis

Split into fixed system / variable system / sample residue, observed vs. inferred.

04Direction generation

Produce 2+ candidates that differ on real axes, not cosmetic variants of one idea.

05Direction evaluation

Score each candidate against the brief on named, observable dimensions.

06Selection

Choose one direction (or shortlist) with a stated reason tied to the evaluation; log what was rejected and why.

07Critiqueconditional

If the selected candidate has an observable mismatch or defect, state it in checkable terms.

08Revisionconditional

Regenerate against a stated critique or client feedback — capped, not an open-ended loop.

09Generation

Produce the actual asset(s) for the selected, post-revision direction.

10aClient feedbackconditional · new

A human/client reviews the delivered artifact in their own words; feedback is translated into concrete changes before revision. From the manager-provided discussion — not in either prior source.

10Final output

Return the asset with a short, checkable rationale — no hidden reasoning trace. May follow generation directly, or a client_feedback → revision loop.

06

Worked example — coffee shop launch post recovery

One of four proposed trajectories in CURIFY_TRAJECTORY_EXAMPLES.jsonl (vd-coffee-0001), shown in full below because it demonstrates the discussion's wrong result → detect → diagnose → change → verify recovery pattern: a candidate is generated, evaluated as a brief mismatch, rejected with a stated reason, and a separate defect on the winner is caught and fixed in one capped revision.

domain: coffee_shop 8 steps outcome: revised_success
brief_understandingstep_01

Parse into target attributes: warm + calm mood, minimalist style, 1:1 format, avoid stock latte-art cliché.

direction_generationstep_03

Generate two candidates on distinct axes — (A) warm neutral type-led, (B) high-saturation duotone poster style — to cover a genuine spread.

direction_evaluationstep_04

Candidate B's saturation and headline weight read energetic/loud, not calm — an observable mismatch against the brief, not a taste call.

Evaluation: A aligns with warm+calm+minimalist. B fails on both mood and style.

selectionstep_05

Select Candidate A. Reject Candidate B with the evaluation's stated reason, logged rather than silently dropped.

critiquestep_06

At Instagram thumbnail scale (161×161px), the linework accent overlaps three letterforms of the wordmark — a checkable production defect.

revisionstep_07

Regenerate once with the accent repositioned below the wordmark. Palette, layout, and type untouched — those already passed brief-alignment.

Result: wordmark legible at thumbnail scale; brief-alignment unchanged from the approved A.

final_outputstep_08

Return A-v2 — warm-neutral, type-led direction, thumbnail-legibility defect fixed in one revision pass.

Client-feedback loop — chili oil packaging before → feedback → after

The new stage from the manager-provided discussion, added to vd-packaging-0001 (steps 08–10) in this update: a human/client reviews a delivered artifact in their own words, and the feedback is translated into concrete, checkable design changes.

07

Benchmark — three layers, never one score

A single final image can't reveal whether the brief was understood or a weak candidate was caught. Full 18-dimension table with automated/human split is in BENCHMARK_PROPOSAL.md.

1

Step-level

Is each individual decision/evaluation/critique good on its own, given the state at that point?

brief understanding reference relevance reference understanding visual-system extraction critique correctness tool-call correctness
2

Trajectory-level

Does the sequence hang together — did evaluation actually drive selection, did critique or client feedback actually get addressed by revision?

direction diversity selection quality revision effectiveness tool / action efficiency recovery rate / quality turns to completion cost / efficiency cross-asset consistency
3

Final-output

Does the deliverable match the brief — necessary, but never treated as sufficient on its own.

direction-to-brief alignment final visual quality production readiness human preference

Recovery rate, tool-call correctness, turns to completion, cost, cross-asset consistency, production readiness, and human preference are new in this update, from the manager-provided discussion. This is the small internal pilot benchmark (11+ dimensions, 10–20 tasks) — not the larger, not-yet-built future Curify Design Agent Benchmark (see BENCHMARK_PROPOSAL.md §8).

08

Semantic robustness — don't memorize the interface

A caveat from the manager-provided discussion: trajectory SFT on one fixed tool schema risks teaching token-matching, not tool-use semantics. The fix is deliberate perturbation testing — not built yet, recorded here as a requirement for any Phase 1 evaluation. Full detail in BENCHMARK_PROPOSAL.md §4.

Perturbation

Tool rename. Same capability, different tool name across otherwise-identical trajectories.

Perturbation

Schema perturbation. Same tool, different argument shape — e.g. count vs. num_candidates.

Perturbation

Tool ordering change. Same available tools, presented in a different order than at training time.

Perturbation

Alternate generators / sources. Different backend behind the same tool name and schema.

Scoring question: not "did it call the exact same tool," but "did it still know when this kind of capability was needed."

09

Workflow × data × evaluation moat

The discussion's strategic argument: don't compete as another generic image generator or prompt-to-design tool — the underlying model stays replaceable (Claude / GPT / Gemini / OSS). What's defensible is workflow, trajectory data, and evaluation. Recorded as a strategic hypothesis, not a product decision made in this research.

Moat

Workflow moat. The workflow library — knowing how a real design task moves from requirement to deliverable.

Moat

Trajectory data moat. Logged decisions, recoveries, and client-feedback loops — not just final images.

Moat

Evaluation moat. The benchmark and judge system built on that data — potentially an asset in its own right (future Curify Design Agent Benchmark, not yet built).

Phase 0 → Phase 1

Phase 0 — benchmark first, training later

Test whether the benchmark dimensions are gradable by hand before collecting any SFT data. No trajectory-SFT training should start before this shows the dimensions are usable — supervision that can't be evaluated can't be trusted.

10–20Creative Exploration tasks
2–3domains, not all at once
100%manually reviewed trajectories
  • Explicit intermediate outputs required — final-image-only logs can't be step- or trajectory-graded.
  • Deliberately include both clean successes and failed/revised examples.
  • Human review first; only then check whether an LLM-judge tracks that human judgment on the automatable subset.

Phase 1 — possible MVP, only if Phase 0 succeeds

Not a committed plan — the source discussion's proposed next-stage shape, recorded for reference. Requires a data-provenance/compliance check on the teacher model before it starts.

300–500real design briefs
4–8teacher trajectories per brief
2k–4ktotal trajectories, top 20–30% selected
  • Same harness/tools given to teacher and student; blind teacher-vs-student evaluation.
  • Dimensions: task success, visual quality, brand consistency, tool-call correctness, recovery rate, turns to completion, cost, human preference.
  • Train a permitted/open-weight student — verify teacher-model/provider terms first.
