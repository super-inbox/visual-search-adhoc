## 1. Executive Summary（执行摘要）

过去三天，围绕管理层提出的"搜索质量不稳定、搜索后业务转化不清楚、能否用 Hybrid Search 改善"三个问题，完成了三条并行调查：**搜索质量评测**、**搜索到生成转化的可测量性审计**、**Hybrid Search 技术可行性审计**。三项工作均为静态/离线调查与设计工作，未修改任何生产代码，未上线任何新功能。

**核心发现**：

1. **搜索质量确实存在系统性问题，不是个别 case**。用新建的 326 条真实场景查询基准测试，综合失败率（PARTIAL+FAIL）达到 **74.8%**，与更早的 328 条基准测试（71.65% 综合失败率）方向一致，说明问题稳定存在、可复现，不是评测口径偶然导致。
2. **失败原因是四类性质完全不同的问题，且 Hybrid Search 只能解决其中一部分**。经拆解，检索排序问题占 31.6%、查询理解/改写问题占 29.1%、目录内容缺口占 27.5%、词义歧义占 11.9%。Hybrid Search（外部图片兜底）只能直接缓解"目录内容缺口"这一类（约占问题总量的四分之一），对排序问题和改写偏移问题**没有直接帮助**，需要配合其他技术手段。
3. **目前无法可靠回答"搜索是否带来生成"这个业务问题**。搜索到点击可以做近似统计，点击到生成完全没有打通，根本原因是系统里不存在贯穿全链路的 `search_id`。在补齐这个字段之前，任何关于 Hybrid Search 上线效果的判断都存在"点击率涨了、但生成量其实跌了"却被误判为成功的结构性风险。
4. **Hybrid Search 在技术上可行，且已有沿用价值的既往设计基础**，但当前代码库里零实现（没有外部图片供应商接入、没有跨来源结果合并逻辑、没有相关埋点），距离可以安全上线还有明确的、未完成的前置工作（供应商合规评审、埋点改造、离线实验、灰度验证）。

**建议方向**：不直接进入开发实施，先完成"管理层对齐 → Hybrid Search 离线评测 → 埋点改造 → 再进入 MVP 开发"的分阶段路径（详见第 10 节）。

## 2. Manager Requirements（管理层需求与调查目标）

管理层提出的问题分为两个性质不同的问题域，本次调查从一开始就将两者分开处理，避免混为一谈：

### 2.1 搜索质量问题（Search Quality）

- 现有搜索结果是否始终令人满意？
- 是否存在低结果 / 零结果的情况？
- 哪类用户查询会失败？
- 问题出在查询理解、检索、排序，还是内容本身缺失？
- Hybrid Search 能否改善"内容缺失"这类问题？

### 2.2 业务影响测量问题（Search Business Impact）

- 用户搜索之后，是否能确认发生了点击？是否能确认发生了生成？
- 当前系统能否测量"搜索 → 点击 → 生成"这条链路？
- 如果不能，需要补充哪些埋点？

### 2.3 提出的技术方向（Hybrid Search）

管理层提出的具体方案：当内部搜索返回结果数为零或很少时，**并行**触发 LLM 查询改写与外部图片搜索（Google Image Search 或合规替代方案），再将两路结果合并展示，同时保留外部链接、提升内容覆盖率。

这三个问题域分别对应本报告第 4-5 节（搜索质量）、第 6 节（业务影响测量）、第 7 节（Hybrid Search 可行性）。

## 3. Investigation Approach（调查方法总览）

```
Search Optimization Investigation（搜索优化调查）
│
├── Search Quality Evaluation（搜索质量评测）
│     用新建的真实场景查询基准，量化"现在到底有多差、差在哪里"
│
├── Search Funnel Measurement（搜索转化漏斗测量审计）
│     核查现有数据/埋点能否回答"搜索是否带来点击和生成"
│
└── Hybrid Search Feasibility（Hybrid Search 技术可行性）
      核查提出的技术方案在现有代码架构下如何落地、风险是什么
```

三部分并非孤立并列，而是**互为前提、互相校验**的关系：

- 搜索质量评测（左）回答"值不值得投入""该投入在哪类查询上"，为 Hybrid Search 的候选查询集提供了具体的、有证据支撑的输入（详见第 4.6 节的 Hybrid Search 候选集）；
- 转化漏斗测量审计（中）回答"如果做了 Hybrid Search，怎么知道它有没有效果"——这项审计独立发现，**在没有 `search_id` 的前提下，即使 Hybrid Search 真的提升了点击率，也无法排除生成量同时下降的可能**，这直接决定了 Hybrid Search 不能仅凭点击率数据做上线判断；
- Hybrid Search 技术可行性审计（右）回答"技术上能不能做、该怎么做、风险在哪"，其"上线前必须补齐的埋点清单"与中间那部分审计的结论完全重合（都指向 `search_id`），两条独立调查线**互相印证**了同一个结论，而不是各说各话。

三部分合起来，构成一个完整的"能不能做、该不该做、值不值得做"的决策依据链条。

## 4. Search Quality Evaluation（搜索质量评测）

### 4.1 既往 300+ 简单查询基准

在本次三项调查开始前，已有一版基于历史"简单词头种子库"（`05_simple_head_term_seed_bank_2026-07-07.csv`）建立的 328 条查询基准，于 2026-07-15 针对生产环境完成过一轮完整的自动化相关性评测（`docs/daily_report/7.15/easy-query-production-baseline-v1/`）：

- **总体结果**：PASS 93 条（28.35%）、PARTIAL 106 条（32.32%）、FAIL 129 条（39.33%），综合失败率 71.65%。
- **平均分 34.54，中位数 23.0**——中位数明显低于均值，说明大量查询集中在低分区间，不是被少数极端案例拉低平均。
- **零结果 12 条**（按规则一律记 FAIL）；**低结果（非零但结果稀少）43 条**，经逐条独立判断（并非自动记 FAIL）得到 PASS 13 / PARTIAL 15 / FAIL 15，证明"结果少"不等于"一定不相关"，也说明低结果查询本身就是一个需要单独关注、不能用一刀切规则处理的群体。

这一版基准建立了本轮调查复用的评分方法论基础（rubric-v1.1：结果级 RELEVANT/PARTIALLY_RELEVANT/IRRELEVANT/UNJUDGABLE 判定 + 排名加权公式 + drift/intent 扣分 + 机械化 PASS/PARTIAL/FAIL 分档规则），但其查询来源本身是为"内容生成长尾扩展"设计的词头库，包含大量抽象风格词（如"极简""复古"）、材质修饰词（如"cork""金属"）、受众词（如"学生""宝妈"）等**不代表真实用户在视觉搜索产品中会输入的查询**，作为"当前搜索质量到底如何"的代表性样本存在结构性偏差。

### 4.2 为什么要新建 Easy Query Benchmark v2

为了让评测结果真正反映"真实用户在视觉搜索产品中会输入的简单查询"，在只读引用既有词头库作为审查素材、原始文件全程不做任何修改的前提下，重新设计了一版 326 条查询基准，围绕四个真实使用场景组织：

- **Creative / Cultural / Merch**（创意文创/潮玩周边）
- **Brand / Business Visual Assets**（品牌商业视觉资产：包装、标签、名片、菜单等）
- **Marketing / Ecommerce**（营销电商物料：横幅、传单、海报、社媒内容）
- **Education / Learning Material**（教学学习材料：识字卡、练习册、图表、证书）

**设计原则**：每条查询是简单名词或短语（不含风格/材质/人群修饰语）、有清晰单一的视觉目标、严格排除抽象风格词/泛化设计术语/受众词/歧义裸词四类禁用词（326 条全部通过程序化核查，零违反）、中英双语对照（各占约一半）。四个场景目标各占 25%，实际分布高度均衡（82/82/82/80）。

### 4.3 测试方法

评测复用与 7/15 基准**完全相同**的评测流水线与配置，确保结果可直接对比：同一份生产目录快照（catalog_size=3209）、`LOW_RESULT_THRESHOLD=5`、模型 gpt-4o-mini、temperature=0.4、Mode D（内部检索 + LLM 改写，均为生产环境已上线能力）、锁定的 rubric-v1.1 评分引擎（与 7/15 版本字节级一致）。全部 326 条查询针对生产环境真实执行，326/326 采集成功，0 错误、0 超时。

### 4.5 结果说明

新旧两版基准的综合失败率（74.8% vs. 71.65%）方向一致、量级接近，**两次独立评测互相印证了同一个结论：当前搜索质量的问题是系统性的，覆盖四个真实使用场景，不是某个边缘查询或评测口径造成的假象**。

四个场景失败率虽然都超过 65%，但差距不大，说明这不是某一类内容特有的问题，而是当前"纯 token/关键词检索 + LLM 改写"架构在多个场景下共同暴露的结构性短板。Creative/Merch 场景失败率最高（82.9%），Education 场景零结果查询最集中（34 条零结果中 16 条落在此场景）。

### 4.6 Hybrid Search 候选查询集

基于本次评测的完整结果，产出了一份 80 条查询组成的 Hybrid Search 验证候选集（`HYBRID_SEARCH_CORE80_CANDIDATE_SET.csv`），四个场景各 20 条，按"零结果查询、低结果查询、代表性失败案例、健康基线查询（回归防护）"四类构成，并逐条标注了预期失败模式、Google 图片兜底是否可能有帮助、LLM 改写是否可能有帮助。这份候选集是后续若要执行 Hybrid Search 离线实验时的直接输入，无需重新筛选。

## 5. Root Cause Analysis（根因分析）

对全部 244 条 FAIL/PARTIAL 记录做了根因归类（规则化方法，基于结果数、是否触发改写、独立相关性判定文本的联合判断），得到四类性质完全不同的根因：

### 5.1 检索/排序问题（Retrieval / Ranking）—— 77 条，占比 31.6%

**定义**：目录中可能存在相关内容，但少数高频、标签覆盖面广的"泛化模板"（如食物涂鸦贴纸、文创周边 mockup、时尚电商、品牌 VI 展板等）在排序中系统性压过了真正相关但数量较少的精准内容。

**典型例子**：查询"吉祥物"命中的是"器官健康信息图"系列，与吉祥物毫无关系；"periodic table"（元素周期表）命中的是"绝命毒师人物 MBTI 卡"系列。这类失败中很多查询**根本没有触发 LLM 改写**，说明问题出在基础检索排序本身，而不是改写环节。

**Hybrid Search 能否解决**：**不能**。这类问题的本质是"目录内容可能已经存在，缺的是把它排到前面的能力"，外部图片源不解决内部排序问题。真正的解法是重排序（reranking）能力，超出 Hybrid Search 本身的范围。

### 5.2 查询理解/改写问题（Query Understanding / Rewrite）—— 71 条，占比 29.1%

**定义**：LLM 改写触发后，生成的改写候选丢失了原始查询的核心约束，导致检索路径大幅扩张、结果集从个位数暴涨到成百上千条，但相关率不升反降。

**典型例子**："globe"（地球仪）触发改写后结果数暴涨到 3205 条，全部与地球仪无关（命中"领袖人物 MBTI"系列）；"drink bottle" 暴涨到 3134 条；"statue" 暴涨到 2748 条，其中仅 1 条真正相关。

**Hybrid Search 能否解决**：**不能直接解决，但方向相关**。这是改写机制本身的问题，外部图片兜底不能修复一个内部逻辑本身跑偏的环节；真正需要的是收紧改写候选与原始查询主体的绑定约束（改写治理），这与 Hybrid Search 是两件独立的工程工作，但两者共享同一个触发点（`LOW_RESULT_THRESHOLD` 判断块），值得放在同一轮工程规划里统一考虑。

### 5.3 目录内容缺口（Catalog Gap）—— 67 条，占比 27.5%（含全部 34 条零结果查询）

**定义**：目录中确实不存在与查询对象匹配的内容/模板族——这是**唯一**一类"内容本身就没有"的问题，而非排序或改写能修复的问题。

**典型例子**：证书（证书/certificate/荣誉证书/毕业证）、优惠券、白板、显微镜、毛绒玩具、盲盒等，无论中英文、无论是否触发改写，均返回零结果或仅命中完全无关的弱相关内容。

**Hybrid Search 能否解决**：**这是 Hybrid Search 唯一能够直接、明确解决的一类问题**。真实世界常见实物/文档类查询有充分的外部图片搜索覆盖，外部兜底可以在目录没有对应内容时提供可用的参考图片。这也是本次调查里 Hybrid Search 投入产出比最清晰的一类场景。

### 5.4 意图歧义 / 词义碰撞（Ambiguous Intent）—— 29 条，占比 11.9%

**定义**：查询词本身在目录的标签体系中存在多个不同含义，且系统性地命中了错误的那个。

**典型例子**："咖啡杯/coffee cup" 命中"World Cup"世界杯球队海报系列；"标志/logo" 命中"landmark"地标建筑；"charm" 命中"charming character"迷人角色而非首饰吊坠；"black friday banner" 命中 Marvel 角色"Black Widow"。

**Hybrid Search 能否解决**：**部分帮助，但不是根本解法**。外部图片搜索理论上可以返回正确义项的图片，但前提是先做意图判别——如果不先解决"这个词到底指哪个意思"，外部搜索会继承同样的歧义。根本解法是在检索前增加意图判别环节，而不是仅靠关键词匹配。

### 5.5 小结：Hybrid Search 不是万能解法

四类根因大致均分（31.6% / 29.1% / 27.5% / 11.9%），但只有"目录内容缺口"（27.5%）是 Hybrid Search 能够直接、明确解决的问题类型。这意味着：**即使 Hybrid Search 完整落地且效果理想，也只能改善约四分之一的失败查询，其余约四分之三仍需要排序能力提升、改写治理、意图判别等其他独立的技术投入才能解决**。这是本次调查最需要向管理层明确传达的一点，避免"上了 Hybrid Search 就能解决搜索质量问题"这种过高预期。

## 6. Search → Click → Generate Measurement Audit（搜索业务影响测量审计）

### 6.1 当前数据可用性

对承载搜索埋点与生成记录的后端仓库（`curify-studio`）做了严格只读的静态代码审计（未执行 SQL、未连接生产数据库、未修改任何文件）。核心发现：**系统里没有独立的搜索日志表**，所有搜索行为都作为通用事件写入一张 `user_interactions` 表，通过 `action_type` 区分是否为搜索事件（`SEARCH`/`SEARCH_NORESULT`/`SEARCH_LOWRESULT`），查询文本本身塞在一个通用的 `content_id` 字符串字段里，而不是独立字段。

### 6.2 Admin Dashboard 现状

管理后台"Business Metrics"标签页下有三张与本次调查直接相关的表：

- **Search Queries**（近 7 天）：按查询词展示搜索次数、无结果占比、点击归因——是唯一能回答"搜索是否带来点击"的表格。
- **Engagement Funnel**（近 7 天）：DAU→浏览→点击→搜索→Generate/Remix 等，但每一环只是"该用户在窗口内是否发生过该行为"的布尔标记，不是按时间顺序验证的单用户路径。
- **Surface Cohorts**：把"搜索过的用户"群体与"是否有过生成行为"的群体做交叉统计——是全系统**唯一**把搜索和生成联系起来的地方，但只是"同一周内是否都发生过"的群体相关性，不是"某一次搜索导致某一次生成"的因果链路。

### 6.3 当前归因等级

| 链路环节 | 归因等级 | 说明 |
|---|---|---|
| Search → Click | **近似可测** | 靠 `COALESCE(user_id, session_id)` + 5 分钟时间窗做启发式关联，存在已知失效场景（同窗口多次搜索归因错误、`/search→/topics` 跳转导致点击事件完全丢失、健康的未收窄搜索根本不产生埋点事件） |
| Click → Generate | **无法可靠测量** | 点击"生成"按钮的埋点事件与真实生成任务记录表 `project` 由完全不相干的两段代码分别写入，之间没有任何共享键，连时间窗启发式都没有实现 |
| Search → Generate（单次实例级别） | **无法可靠测量** | 唯一存在的信号是群体层面、同周共现的相关性统计，不满足"某次搜索导致某次生成"这种有时序、会话级的要求 |

一个额外的结构性缺陷：生成记录表 `project` **没有 `session_id` 字段**，只有 `user_id`。这意味着即使未来补齐了关联字段，**匿名（未登录）用户的生成行为也天生无法与其匿名搜索/点击历史关联**——这部分流量的转化会被完全漏掉。

### 6.4 为什么需要 `search_id`

这是本次审计反复强调的核心结论：**没有一个贯穿曝光→点击→生成全链路的稳定唯一标识，后面所有精细化指标都无从谈起**。当前系统完全没有这个字段（全仓库搜索 `search_id`/`searchId` 零命中，在负责渲染 `/search` 页面的前端仓库中同样零命中）。

更关键的是，这一发现直接决定了**不能仅凭点击率（CTR）判断 Hybrid Search 是否成功**。审计确认了两个真实存在（非假设）的机制，足以让 CTR 报表数值在生成效果没有改善、甚至恶化的情况下"看起来在涨"：

1. 健康的、未被收窄的正常搜索根本不产生埋点事件，导致"搜索总量"这个分母本身被低估、偏向失败案例；一旦 Hybrid Search 带来更多"外观吸引人但导向站外"的结果点击，点击率分子上升而分母依然被低估，CTR 数字会被结构性推高。
2. 搜索和生成之间没有可靠链路——如果 Hybrid Search 增加的点击流向了不支持"生成"能力的外部结果，Admin Dashboard 的 CTR 表格会显示"提升"，而唯一与生成相关的信号（群体周相关性）最多只能显示"同周整体比例略有下降"，无法证明也无法排除这是不是该次实验造成的。

### 6.5 短期方案（不改代码，基于现有数据近似回答）

复用已在生产环境跑通的 Search→Click 归因模式，向后延伸一跳：对同一 `user_id`（**做不到匿名用户**，因为 `project` 表没有 `session_id`），在约定的时间窗口（如 30 分钟，未经验证，需产品/工程共同拍板）内查找是否有 `project.status='COMPLETED'` 的新记录。不需要改动任何产品代码，只需一条新的分析 SQL。

**局限性（必须向管理层明确说明，避免误用）**：完全无法覆盖匿名用户；时间窗是估算值，没有历史数据支撑；多次搜索/多次点击导致的归因混淆问题会被放大（在已有的 Search→Click 误差上再叠加一跳）；搜索埋点本身的低估问题依然存在，算出来的转化率绝对值不可信，只能看相对趋势。**结论：短期方案能给出方向性、有明显偏差警告的近似数字，可用于内部粗略监控，不建议作为 Hybrid Search 上线与否的决策依据。**

### 6.6 中期方案：引入 `search_id`

核心改造只有一件事：**在用户发起一次搜索的那一刻生成一个稳定的 `search_id`，并让它贯穿这次搜索所引发的曝光、点击、生成全部事件**。具体包括：搜索事件埋点扩展（新增 `search_id` 列，同时修正"只有失败/收窄搜索才埋点"的问题，改为每次搜索都埋点）；新增目前完全不存在的结果曝光事件；点击事件补充 `search_id` 透传；生成记录表 `project` 补充 `search_id`、`source_result_id`、`session_id` 三个字段。

打通后，原来需要"猜身份+猜时间窗"的近似关联，变成一次精确的主键 JOIN，同时解决短期方案的全部核心局限：覆盖匿名用户、消除时间窗猜测误差、消除多次搜索/点击的归因混淆。

### 6.7 Hybrid Search 上线的最小埋点要求

上线 Hybrid Search 前必须补齐的 P0 字段：`search_id`、`search_mode`（区分内部 vs. 混合搜索）、`result_source`（区分内部/外部结果）、`result_rank`、`result_click`、`generate_click`、`generation_success`（均通过 `search_id` 关联，而非猜测式时间窗）。这份清单与 Hybrid Search 技术审计（第 7 节）独立得出的埋点要求完全一致，两条调查线相互印证。

**结论：搜索到点击目前只能近似回答；搜索到生成目前基本不能回答，短期方案只能给出一个覆盖不全、窗口未经验证的粗略估算。要想真正、可靠地回答管理层的业务问题，`search_id` 埋点改造不是锦上添花的优化，而是必要前提。**

## 7. Hybrid Search Feasibility（Hybrid Search 技术可行性）

### 7.1 当前搜索架构

Curify 的 `/search` 页面是一个 Next.js Server Component，**没有数据库、没有独立搜索索引服务**（未使用 Elasticsearch/Algolia 等）。检索方式是对静态 JSON 文件做请求内的线性扫描打分。链路顺序：

1. 用户输入查询 → 归一化 → 分词（含中文字符 bigram 回退）
2. 第一次内部检索（线性打分，严格/宽松两级匹配）
3. 计算结果数量（`initialThinCount`）
4. **若结果数 < 5**（`LOW_RESULT_THRESHOLD=5`，已存在于生产环境），触发 LLM 查询改写
5. 用改写后的最多 10 条路径重新检索，按记录 ID 合并（同源合并，取最高分）
6. 结果渲染给客户端组件，上报埋点

**关键结论：LLM 改写功能已经上线生产环境，不是本次要新建的能力**。本次要新增的是"外部图片搜索"这一条腿，以及把它和已有的 LLM 改写能力**并行**运行、再合并展示的机制。

这个功能也不是全新构想——代码库中已有一份更早期的设计提案（"Extension C — Hybrid Google results"，2026-06-27 归档），详细起草了几乎完全相同的方案（触发阈值、缓存策略、只加超链接不代理图片、回流 CTA、埋点、熔断条件），但**该文档只是战略提案，代码库中零实现痕迹**——全仓库搜索确认没有任何 Google Custom Search 客户端代码。本次审计独立验证了这份提案的技术可行性，并补充了实验设计细节，不直接采信其结论为既定事实。

### 7.2 提出的 Hybrid Search 架构

```
用户查询
   │
   ▼
内部检索（现有能力，线性打分）
   │
   ▼
低结果判断（沿用现有 LOW_RESULT_THRESHOLD=5 阈值作为候选起点）
   │
   ├── 结果数 ≥ 5 → 内部结果直接展示（不触发下方流程）
   │
   └── 结果数 < 5 → 并行触发：
          ├── LLM Rewrite（已上线能力，沿用现有改写逻辑）
          └── External Image Search（Google Image Search 或合规替代方案，全新能力）
                    │
                    ▼
              受控合并（Controlled Merge）
              内部结果优先展示，外部结果仅填补空缺
```

有两个明确的插入点：**服务端触发点**——现有的低结果判断代码块，今天只触发 LLM 改写，未来应在此并行触发外部图片搜索调用（而非顺序执行），这正是管理层要求的"LLM Rewriter 和 Google Image Search 同时跑"；**客户端渲染点**——现有的"零结果"UI 分支（目前只渲染一个话题推荐条），是新增"来自外部的灵感"结果条的天然挂载位置，同时应扩展到"结果数低但非零"的情况。

### 7.3 为什么不能直接上线

四个不能跳过的原因：

1. **供应商/合规未落地**：代码库中没有任何 Google Custom Search API 的密钥约定、账号、配额或价格证据，必须先走合规评审（缓存时长、署名要求是否符合供应商条款）。
2. **零跨源合并逻辑**：今天代码里唯一的"合并"是同源合并（多条 LLM 改写路径的合并），没有任何代码合并过两个不同来源的结果集，这是要从零设计和构建的核心逻辑。
3. **归因埋点缺失**：与第 6 节完全一致的结论——没有 `search_id`，搜索到点击到生成的转化链路今天只能靠启发式时间窗拼接，在同时展示内部+外部结果时会进一步失真。
4. **离线数据不能代替线上实验**：即使完成离线相关性/安全性评测，也无法证明真实的点击率或生成率提升，必须走完分阶段上线才能看到真实业务效果。

### 7.4 推荐的 MVP 原则

- **内部结果始终优先展示**，外部结果只填补空缺、不替换内部内容——内部目录是 Curify 真正的产品，外部内容不能挤占它。
- **外部兜底仅在内部结果稀薄时触发**，结果数 ≥ 5 时默认不触发外部调用（沿用现有阈值作为起点，最终阈值需通过离线实验在 T0/T3/T5 三个候选之间比较后确定）。
- **明确来源标签**：外部结果区块整体标注"来自外部的灵感/参考"，每张卡片额外带来源域名角标，双重标注降低误认风险。
- **保留外部原始链接**：不代理、不改写、不跳转拦截外部图片，直接超链接到原始来源，兼顾版权合规与用户信任。
- **避免误导性用户操作**：外部结果只允许"点击跳转到原始链接"，禁止编辑、直接生成、下载、复制提示词等内部专属操作；建议用全新的、独立的卡片组件渲染外部结果，不复用现有内部卡片组件（现有组件默认假设图片来自 Curify CDN、跳转到内部路由，与外部结果的数据形状不兼容，复用会有"意外暴露内部专属按钮"的风险）。
- **外部供应商失败不能影响内部结果**：内部结果独立计算、始终渲染，不因外部调用失败/超时而受影响，这是硬性约束而非"尽力而为"。

### 7.5 最大风险

**核心风险：点击率（CTR）上升，但"搜索→生成"转化率下降。** 外部链接可能因内容更丰富、更贴合长尾查询而吸引点击，但用户点击后跳转到第三方页面，该页面没有动机把用户导回 Curify——用户的视觉浏览需求被"满足"了，但没有触发任何生成行为。这正对应管理层业务问题的核心："搜索后用户是否点击**并生成**"，而不仅是"是否点击"。其他重大风险还包括版权/展示合规风险（需法务评审）、内部点击蚕食、外部图片失效/供应商中断风险、成本与配额风险，完整清单见 `HYBRID_SEARCH_RISK_REGISTER.csv`（22 项）。

因此技术审计与测量审计得出完全一致的建议：**线上实验的主指标必须是 Search-to-Generate Rate 和 Generation Success Rate，CTR 只能作为诊断性辅助指标；即使 CTR 表现良好，只要生成相关指标持平或下降，就应判定实验未通过**。

## 8. Key Conclusions（关键结论）

1. **搜索质量是真实存在的问题，不是感觉或个案**：两版独立基准测试（328 条 / 326 条）综合失败率均超过 70%，方向一致、可复现。
2. **最大的问题不是单一原因**：检索排序（31.6%）、查询理解/改写（29.1%）、目录内容缺口（27.5%）、意图歧义（11.9%）四类原因大致均分，需要四种不同的技术手段分别应对。
3. **Hybrid Search 值得探索，但预期要设对**：它能直接、明确解决的只有"目录内容缺口"这一类（约四分之一的失败查询），不能替代排序能力提升、改写治理、意图判别这三项独立工作。
4. **当前无法可靠测量业务影响**：搜索到点击近似可测，点击到生成完全没有打通，核心缺口是 `search_id`；在补齐之前，任何仅凭点击率做出的 Hybrid Search 效果判断都有被误导的结构性风险。
5. **上生产前必须完成的前置工作**：供应商合规评审与账号落地、`search_id` 为核心的埋点改造、跨来源合并/去重逻辑的实现、离线评测验证、分阶段灰度上线——这些均**尚未开始**（详见第 10 节）。

### 建议分阶段推进

**Phase 1：管理层对齐** —— 基于本报告确认：(a) 是否认可"Hybrid Search 只能解决约四分之一失败原因"这一预期设定；(b) 是否认可"上线判断必须以 Search-to-Generate / Generation Success 为主指标，而非仅看 CTR"这一决策原则；(c) 优先级排序——是否需要同时启动排序能力/改写治理等其他三类根因的独立工作。

**Phase 2：Hybrid Search 离线评测** —— 基于已产出的 80 条候选查询集，在真实供应商接入前，用受控的离线实验对比"仅内部""仅改写""仅外部兜底""并行 Hybrid""受控 MVP" 等模式的相关性与安全性表现，验证方案有效性后再决定是否投入工程实现。

**Phase 3：埋点改造** —— 落地以 `search_id` 为核心的埋点方案（曝光/点击/生成全链路打通），这是后续任何可信的效果判断的前提条件，独立于 Hybrid Search 是否最终上线都有价值（能同时修复当前"搜索总量被低估"的问题）。

**Phase 4：MVP 实现** —— 在前三个阶段都完成后，才进入代码实现阶段：供应商客户端、合并/排序逻辑、新卡片组件、缓存层、熔断开关，全部置于 Feature Flag 之后、默认关闭。

**Phase 5：受控灰度上线** —— 完成功能开发后，按"预发布环境验证 → 小流量 A/B → 逐步放量"的顺序上线，每一步都设置护栏指标（外部流失率、内部点击蚕食率、延迟、成本、错误率）与可用的一键回滚开关。

**为什么不能跳过验证直接开始实施**：技术审计与测量审计都明确指出，在没有真实供应商响应数据、没有埋点、没有离线相关性/安全性验证的情况下直接写代码上线，会导致"不知道效果好不好、也不知道出了问题算谁的"的局面——尤其是"CTR 上升但生成下降"这种risk在当前测量能力下是不可见的。分阶段推进的每一步都对应一个明确的"继续/停止"判断依据，这是本次调查反复强调、需要在管理层对齐阶段就达成共识的原则。

## 11. Limitations（局限性说明）

- **Google Image API（或合规替代方案）尚未接入**，本报告中关于外部结果质量、真实延迟、真实成本的判断均基于同类服务的一般性认知，未经真实供应商响应验证。
- **Hybrid Search 尚无任何生产部署**，第 7 节的架构方案是设计建议，未落地为可运行代码。
- **未进行任何形式的线上 A/B 测试**，第 6、7 节涉及的转化率、CTR 等指标结论均基于静态代码审计推导的"能否测量"判断，不包含任何真实业务数据的实际数值。
- **搜索到生成的归因依赖尚未完成的埋点改造**——本报告第 6 节给出的短期近似方案本身也有明确局限（无法覆盖匿名用户、时间窗未经验证），不能替代 `search_id` 打通后的精确测量。
- **本报告涉及的全部工作均处于调查与规划阶段**，不代表任何功能已经上线、正在开发，或已获得工程资源排期承诺。
