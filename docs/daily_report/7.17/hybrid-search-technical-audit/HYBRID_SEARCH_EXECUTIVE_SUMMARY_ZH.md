# Hybrid Search 技术审计 — 中文执行摘要

审计仓库：`curify-frontend-hybrid-audit`（只读浅克隆）· 分支 `main` · commit `5a59c4b`
审计性质：**纯只读技术审计与实验设计**，未修改任何源代码，未调用任何外部 API（未调用 OpenAI，未调用 Google）。

---

## 1. 当前搜索链路是什么？

Curify 的 `/search` 页面是一个 **Next.js Server Component**（`app/[locale]/(public)/search/page.tsx`），没有数据库、没有独立的搜索索引服务（Elasticsearch/Algolia 等均未使用）。检索方式是**对静态 JSON 文件（`public/data/nano_inspiration.json`）做请求内的线性扫描打分**（`scoreQueryTokens`，page.tsx:470-578）。

链路顺序：
1. 用户输入查询 → 归一化（`lib/query_normalize.ts`、`page.tsx:normalizeForSearch`）→ 分词（含中文字符 bigram 回退，`page.tsx:buildSearchTokens`）
2. 第一次内部检索（线性打分，严格/宽松两级匹配）
3. 计算结果数量 `initialThinCount`（page.tsx:611）
4. **若结果数 < 5**（`LOW_RESULT_THRESHOLD=5`，已存在于生产环境），触发 **LLM 查询改写**（`lib/searchRewrite.ts` 的 `getMultiQueryPaths`，调用 gpt-4o-mini，已上线，非本次新增）
5. 用改写后的最多 10 条路径重新检索，按记录 ID 合并（同源合并，取最高分，多路径命中有 +8%/次、封顶 +40% 的排序加成）
6. 结果序列化给客户端组件 `SearchResultsClient.tsx` 渲染卡片，并上报埋点

**关键结论：LLM 改写功能已经上线生产环境，不是本次要新建的能力。** 本次任务要新增的是"外部图片搜索"这一条腿。

## 2. Google 外部结果应该接在哪里？

有两个明确的插入点（均在调用链图 Deliverable 3 中详细标注）：

- **服务端触发点**：`page.tsx:620-625` 现有的 `if (initialThinCount < LOW_RESULT_THRESHOLD && ...)` 判断块——今天只触发 LLM 改写，未来应在此**并行**（`Promise.allSettled`，而非顺序执行）触发外部图片搜索调用，这正是经理要求的"LLM Rewriter 和 Google Image Search 同时跑"。
- **客户端渲染点**：`SearchResultsClient.tsx:319-329` 现有的"零结果"分支（目前只渲染一个 `TopicStrip` 话题推荐条）——这是新增"来自外部的灵感"结果条的天然挂载位置，同时也应扩展到"结果数低但非零"的情况。

值得强调的是：**这个功能不是全新构想**。`docs/eval-framework-visual-search-benchmark-2026-06-14.md` 文档中的 "Extension C — Hybrid Google results"（2026-06-27 归档）已经详细起草了几乎完全相同的方案——触发阈值、7 天缓存、只加超链接不代理图片、"Make with Curify" 回流 CTA、`nano_external_inspiration_click` 埋点、以及"若 `external_click → curify_create` 转化率 < 8% 则下线"的熔断条件。**但该文档只是战略提案，代码库中零实现痕迹**（全仓库搜索确认没有任何 Google Custom Search 客户端代码）。本次审计独立验证了这一方案的技术可行性，并补充了实验设计细节。

## 3. 为什么不能直接上线？

四个不能跳过的原因：

1. **供应商/合规未落地**：`.env.example` 不存在，仓库中没有任何 Google Custom Search API 的密钥约定、账号、配额或价格证据——"provider unresolved, credentials unresolved, cost unresolved, quota unresolved"，必须先走合规评审（缓存时长、署名要求是否符合 Google 条款）。
2. **零跨源合并逻辑**：今天代码里唯一的"合并"是同源合并（多条 LLM 改写路径的合并），**没有任何代码合并过两个不同来源的结果集**，这是要从零设计和构建的核心逻辑。
3. **归因埋点缺失**：全仓库搜索 `search_id`/`searchId` **零命中**。没有这个字段，"搜索→点击→生成"的转化链路今天只能靠 `(session_id, 查询文本, 粗略时间窗口)` 做启发式拼接，这个拼接在用户重复搜索、长时间浏览后点击、或者同时展示内部+外部结果时都会失真。
4. **离线数据不能代替线上实验**：Core-80 offline 评测（80 查询 × 5 模式）能验证相关性/安全性/工程指标，但**无法证明真实的 CTR 或生成率提升**——必须走完分阶段上线（Deliverable 14）才能看到真实业务效果。

## 4. 需要测试哪五种模式？

| 模式 | 说明 |
|---|---|
| **A — 仅内部** | 干净基线，不含 LLM 改写，不含外部搜索 |
| **B — 仅改写** | 当前生产环境的实际行为（内部检索 + LLM 改写），用于隔离改写本身的贡献 |
| **C — 仅外部兜底** | 内部检索 + 用原始查询做外部图片搜索，不含 LLM 改写，用于隔离外部内容本身的贡献 |
| **D — 并行 Hybrid** | 经理要求的原始方案：LLM 改写与外部搜索并行执行，合并展示，但不含完整的生产安全护栏 |
| **E — 受控 Hybrid MVP** | D 的生产就绪版本：内部结果优先排序、外部结果数量上限、明确来源标签、保留外部原始链接、外部结果禁用内部专属操作（编辑/生成）、超时处理、失败兜底、缓存、去重、Feature Flag、可观测性、熔断开关 |

**只有模式 E 是本审计建议推进上线的候选**，A-D 均为离线对照实验，用于在承诺完整工程投入之前，量化改写和外部搜索各自的独立贡献。

## 5. 推荐的第一版触发规则

沿用现有 `LOW_RESULT_THRESHOLD=5` 的既有阈值作为**候选起点**（即 T5：内部结果数 < 5 时触发），但**明确不锁定为最终值**——需要通过 T0（=0 时触发）、T3（<3 时触发）、T5（<5 时触发）三个候选在 Core-80 离线实验中对比后再决定。已知风险：结果数量高不代表相关性好，结果数量低也不代表相关性差——这是纯计数触发规则的结构性局限，本审计未尝试用相关性打分触发规则替代，因为 Curify 目前**没有任何相关性标注数据**（`Extension B` 文档已确认这一空白）。

---

## 6. 推荐的第一版融合规则

内部结果**始终优先展示**，外部结果只填补空缺，不替换内部内容：

- 内部结果数为 0：允许最多 8-12 条外部结果，整个区块明确标注"来自外部的灵感/参考"
- 内部结果数 1-4：保留全部内部结果在前，剩余首屏位置（12 格布局）用外部结果填充
- 内部结果数 ≥ 5：默认不触发外部搜索（在 T5 阈值下不可达，除非未来改用更宽松的触发规则）

**去重**（MVP 阶段）：按标准化目的地 URL / 标准化图片 URL / 标题+域名组合三种廉价确定性方式，明确说明每种方式的局限（例如无法识别同一图片的不同尺寸变体）。感知哈希、视觉向量相似度等更强的去重手段明确列为**后续阶段**，非 MVP 范围。

**外部结果的操作限制**：只允许"点击跳转到原始链接"，**禁止**编辑、直接生成、下载、复制提示词等内部专属操作——建议用一个**全新的、独立的卡片组件**渲染外部结果，而不是复用现有内部卡片组件，因为现有组件默认假设图片来自 Curify CDN、目的地是 Curify 内部路由，与外部结果的数据形状根本不兼容，复用会带来"意外暴露内部专属按钮"的风险。

---

## 7. 最大风险是什么？

**核心风险：CTR 上升，但"搜索→生成"转化率下降。**

外部链接可能因为内容更丰富/更贴合长尾查询而吸引点击（CTR 上升），但用户点击后跳转到第三方页面，该页面没有任何动机把用户导回 Curify——用户的视觉需求被"满足"了，但没有触发任何生成行为。这正是经理提出业务问题的核心："搜索后，用户是否点击并生成？"而不是"用户是否点击"。

其他重大风险（详见风险登记表，22 项）：
- 版权/展示合规风险（需公司法务评审，本审计不做法律结论）
- 归因埋点缺失（`search_id` 不存在）导致无法可靠衡量上述核心风险
- 内部点击蚕食（外部结果抢占了本应导向内部生成的点击）
- 外部图片失效/挂链风险、供应商中断风险、成本与配额风险

## 8. 上线前必须补哪些埋点？

上线前最小必需字段集合（P0）：`search_id, search_mode, result_source, result_rank, result_click, generate_click, generation_success`。

**其中三项需要全新工程投入，不是简单加字段**：
1. `search_id` —— **今天完全不存在**，需要在服务端每次搜索请求生成一次，并贯穿服务端→客户端→跳转到生成页面的完整链路。
2. 点击→生成的关联 —— "生成"事件今天已经在上报（`ReproduceWorkbench.tsx:233` 等多处已确认存在 `trackAction(tracking, "generate")`），但完全没有携带来源搜索的任何标识，需要通过 URL 参数或类似现有 `WITHIN_INTENT_KEY` 的会话级交接机制补上。
3. `generation_success` —— 今天的"生成"事件只在**点击生成按钮时**触发一次，不区分"点击了"和"真正生成成功了"——这是一个独立于 Hybrid Search 的既有缺口，但会直接影响经理关心的业务问题能否被准确回答。

---

## 9. 为什么最终要看 Search-to-Generate，而不是只看 CTR？

因为 CTR 只能证明"用户对新增内容感兴趣"，而 **Curify 的产品价值来自生成行为，不是点击行为**。如果外部结果吸引了点击但用户点击后离开 Curify、不再返回，CTR 指标会"看起来在涨"，但实际上产品价值（生成量）可能是**下降**的——这是本审计反复强调的 CTR-上升/生成-下降 陷阱模式。因此本审计建议：

- 线上 A/B 实验的**主指标必须是 Search-to-Generate Rate（搜索到生成转化率）**和 Successful Generation Rate，CTR 只能作为诊断性/辅助指标。
- 即使 CTR 表现良好，只要 Search-to-Generate Rate 持平或下降，就应判定实验**未通过**，不能因为 CTR 好看就上线。
- 这与 Extension C 文档中已经设计好的熔断逻辑（`external_click → curify_create` 转化率低于阈值即下线）在方向上完全一致，本审计只是把这一原则明确为整个上线决策的核心判据，而不仅是外部结果区块自身的开关条件。
